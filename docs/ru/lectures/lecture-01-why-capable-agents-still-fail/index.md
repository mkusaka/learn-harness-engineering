# 講義 01. 能力の高いモデルでも失敗する理由

AI の世界ではもう十分わかっているつもりだとします。Claude Pro のサブスクもあるし、GPT-4o の API キーもある。SWE-bench のリーダーボードの数字も暗記済み。そんな状態で、いよいよ実案件を AI エージェントに任せる。自信満々です。結果はどうでしょう。機能は追加したのにテストを壊し、バグは直したのに新しいバグを2つ増やし、20分動いて「完了しました」と誇らしげに言うのに、コードを見れば依頼した内容とまったく違う。

最初に浮かぶ考えは何でしょう。「モデルが弱い。アップグレードしよう」でしょうか。ちょっと待ってください。財布を開く前に考えるべきです。問題はモデルではないかもしれません。

数字を見てみましょう。ベンチマークは驚くほど速く変わります。2025年9月、Anthropic は Claude Sonnet 4.5 が SWE-bench Verified で 77.2% を達成したと発表しました。つまり、ベンチマーク上で非常に強く見えるモデルでも、それは厳選されたタスクでの結果にすぎません。明確な issue の説明と既存のテストがある環境です。普段の開発環境に持ち込むとどうでしょう。曖昧な要件、テストの不足、あちこちに散らばった暗黙の業務ルール。こうした条件では、その数字が自動的に再現されるわけではありません。

しかし、その数字の裏には直感に反する真実があります。

## 同じ馬、違う運命

Anthropic は制御実験を行いました。プロンプトは同じです。「2D のレトロなゲームコンストラクタを作れ」。モデルも同じで、Opus 4.5。1回目は、支援のないむき出しの環境で実行しました。20分、9ドル。ゲームの重要な仕組みがそもそも動きません。2回目は、完全な harness を用いました。planner + generator + evaluator の3エージェント構成です。6時間、200ドル。今度はゲームとして遊べるものになりました。

モデルは変えていません。Opus 4.5 はずっと Opus 4.5 のままです。変わったのは鞍です。

OpenAI の 2026年の harness engineering に関する記事ははっきり述べています。良い harness を持つリポジトリでは、Codex は「信頼できない」状態から「信頼できる」状態へ移る。注目すべきは表現です。「少し良くなる」ではなく、質的な変化だということです。血統のよい馬と同じで、鞍がなくても乗ることはできますが、遠くまでは行けないし、速くも走れないし、落ちるのも驚きではありません。harness とはまさにその鞍です。**モデルの重みの外側にある、あらゆるエンジニアリング基盤のことです。**

## エージェントが本当に詰まる場所

では、具体的には何がうまくいっていないのでしょうか。

いちばん多いのは、そもそもタスクを明確に定義できていないことです。「検索を追加して」と言っても、エージェントはあなたとは別の意味で受け取ります。何の検索でしょう。全文検索ですか、それとも構造化検索ですか。ページネーションは。ハイライトは。そこを詰めていないと、エージェントは推測するしかありません。たまたま当たれば幸運です。外れたら、最初からきちんと指示するより修正コストが高くつきます。レストランで料理人に「魚をください」とだけ言うようなものです。煮付けか、蒸し物か、土鍋かは運任せになります。

たとえ要件をすべて伝えていたとしても、プロジェクトにはエージェントが知らない暗黙のアーキテクチャ規約があります。あなたのチームは SQLAlchemy 2.0 の書き方を標準化しているのに、エージェントはデフォルトで 1.x のコードを書きます。すべての API エンドポイントは OAuth 2.0 を使うべきなのに、そのルールはあなたの頭の中と、3か月前の Slack メッセージの中にしかありません。エージェントには見えていないのです。守りたくないのではなく、そのルールの存在自体を文字通り知らないのです。

環境も落とし穴です。dev 環境が不完全だったり、依存関係が欠けていたり、ツールのバージョンが違っていたりします。エージェントは貴重なコンテキストの枠を `pip install` の失敗や Node のバージョン不一致に費やし、本来解くべき問題に進めません。腕のいい大工を雇ったのに、金槌も釘も平らな作業台も渡し忘れたようなものです。どれだけ有能でも、仕事はできません。

さらに多いのは、そもそも検証手段がないことです。テストがない、lint がない、あるいは確認コマンドがエージェントに伝わっていない。エージェントはコードを書いて、それを見て、問題ないと判断し、「完了」と言います。答えを見せずに宿題を提出させるようなものです。本人は正しいと思っていても、採点すればミスだらけです。Anthropic は興味深い現象も観測しました。エージェントがコンテキスト残量を感じると、早く終わらせようとして検証を飛ばし、最適解ではなく簡単な解を選びがちになります。彼らはこれを「context anxiety」と呼びます。試験時間が尽きそうだと気づいたときに、残りの問題を勘で埋め始めるのと同じです。

複数セッションにまたがる長いタスクは、さらに悪いです。前のセッションで見つけたことが失われるので、新しいセッションごとにプロジェクト構造を調べ直し、コードの組織をゼロから理解し直します。永続状態を持たないエージェントでは、30分を超えるタスクで失敗率が急に上がります。

## 重要用語

こうした場面を実際に見ると、用語は単なる業界用語ではなくなります。

- **Capability Gap**: ベンチマーク上のモデル性能と実タスクでの性能の間にある巨大な隔たりです。SWE-bench Verified で高い pass rate を出しても、要件が曖昧で、アーキテクチャ規約が暗黙的で、検証も不完全な現実の issue で同じ結果になるとは限りません。
- **Harness**: モデルの外側にあるすべてです。指示、ツール、環境、状態管理、検証フィードバック。モデルの重みでなければ、それは harness です。あの「鞍」です。
- **Harness-Induced Failure**: モデルには十分な能力があるのに、実行環境に構造的な欠陥があるために失敗することです。Anthropic の制御実験がすでにそれを示しました。
- **Verification Gap**: エージェントが自分の作業に抱く確信と、実際の正しさとのずれです。終わっていないのに「終わりました」と言う。これは最もよくある失敗パターンです。
- **Diagnostic Loop**: 実行して、失敗を確認して、その失敗を harness の特定レイヤーに帰属させ、そのレイヤーを直して、もう一度実行する。これが harness engineering の中核です。
- **Definition of Done**: テストが通る、lint がきれい、型チェックが通る、といった機械的に検証可能な条件の集合です。明示的な definition of done がなければ、エージェントは自分なりの完了条件を勝手に作ります。

## 何かが壊れたら、まず harness を直す

基本原則はこうです。**何かが壊れたら、いきなりモデルを変えずに harness を確認してください。** 同じモデルが、似た構造のよく整理されたタスクではうまく動くなら、問題は harness にあると考えてください。車の故障でも、いきなりエンジンを疑うわけではありません。まずガソリンが切れていないかを確認します。

具体的な手順は次のとおりです。

**それぞれの失敗を、どのレイヤーの問題かに結びつける。** 「モデルが鈍い」で終わらせないでください。問い直すべきです。タスクは曖昧だったか。コンテキストは足りていたか。検証手段はあったか。失敗を、5つの防御レイヤーのどれかに対応づけてください。5つのレイヤーとは、タスク仕様、コンテキスト提供、実行環境、検証フィードバック、状態管理です。この習慣をつければ、ログに「モデルが十分ではない」という記録が出る頻度はどんどん下がります。

**各タスクに明示的な Definition of Done を書く。** 「検索を追加して」ではなく、たとえばこうです。
```
完了条件:
- 新しいエンドポイント GET /api/search?q=xxx
- ページネーション対応、デフォルト 20 件
- 結果にハイライトされたスニペットを表示
- 新規コードはすべて pytest を通過
- 型チェックが通る (mypy --strict)
```

**AGENTS.md を用意する。** リポジトリのルートに置き、プロジェクトのスタック、アーキテクチャ規約、検証コマンドをエージェントに伝えてください。これは harness engineering の最初の一歩であり、最も ROI が高い一歩です。`AGENTS.md` 1つで、高価なモデルへのアップグレードより効果が出ることがあります。誇張ではありません。

**診断ループを作る。** 失敗を「またモデルがダメだった」で終わらせないでください。harness のどこかに欠陥があるという信号として扱います。失敗のたびにレイヤーを特定し、そこを直し、同じ失敗を二度と起こさないようにします。何回か回すうちに harness は強くなり、エージェントの性能は安定します。道路補修と同じです。穴を埋めるたびに、次の区間は平らになります。

**改善を測る。** シンプルなログを残しましょう。各タスクが成功か失敗か、失敗の原因がどのレイヤーだったかを記録します。何周かすると、どのレイヤーがボトルネックかが見えてきます。そこに集中して手を入れればよいのです。

## 100万行の実験

OpenAI の 2026年の記事では、2025年後半に始まった大胆な実験が紹介されています。Codex を使って、空の git リポジトリから社内向けのプロダクト全体を構築するというものです。5か月後には、リポジトリに約100万行のコードがありました。アプリケーションロジック、インフラ、ツール、ドキュメント、社内 dev ツールまで、すべてエージェントが生成しました。3人のエンジニアが Codex を運用し、約1500件の PR を開いてマージしました。1人あたり平均で1日3.5 PR です。

重要な制約は、**人間が直接コードを書かない**ことでした。これは見せ物ではありません。エンジニアの主な仕事が、コードを書くことではなく、環境を設計し、意図を言語化し、フィードバックループを作ることに変わると何が起きるかを、チームに理解させるためのものです。

最初は、進捗が予想より遅かったそうです。Codex に能力が足りなかったからではありません。環境が十分に整っていなかったからです。高レベルの目標に向かって進むために必要なツール、抽象化、内部構造が足りませんでした。エンジニアの仕事は、設計、コード、レビュー、テストといった小さな構成要素に大きな目標を分解し、それをエージェントに組み立てさせ、その構成要素を使ってより難しいタスクを解放していくことになりました。何かが壊れたとき、修正はほとんどの場合「もっと頑張る」ではありませんでした。「エージェントにはどの能力が足りないのか。その能力を、どうすれば理解しやすく、かつ実行可能な形にできるのか」という問いでした。

この実験は講義の主張を直接裏づけています。**同じモデルでも、むき出しの環境と、完全な harness を備えた環境では、結果が根本的に違う**のです。モデルは変わっていません。環境が変わったのです。

## もっと身近な例

あるチームは Claude Sonnet を使って、中規模の Python Web アプリケーション（FastAPI + PostgreSQL + Redis、約 15,000 行）に新しい API エンドポイントを追加しました。

最初は、たった一文だけを与えました。「`/api/v2/users` 配下にユーザー設定エンドポイントを追加して」。結果はどうだったでしょう。エージェントはコンテキストウィンドウの 40% をリポジトリ構造の調査に使い、見た目はもっともらしいコードを出したものの、プロジェクトのエラーハンドリングのパターンには従わず、古い SQLAlchemy の構文を使い、完了を宣言しました。しかしエンドポイントにはランタイムエラーがありました。次のセッションでは、調査を全部やり直す必要がありました。

その後、彼らは `AGENTS.md` を追加しました。そこにはプロジェクトのアーキテクチャとスタックのバージョンが書かれています。さらに、明示的な検証コマンド（`pytest tests/api/v2/ && python -m mypy src/`）と architecture decision records も追加しました。すると同じモデルが3回の独立した実行すべてで成功し、コンテキスト効率は約 60% 向上しました。

モデルは変えていません。harness を変えただけです。

## 要点

- モデルの能力と実行の信頼性は別物です。血統のよい馬にも、ちゃんとした鞍が必要です。
- 何かが壊れたら、まず harness を確認し、次にモデルを見てください。モデルの変更は最も高くつく選択であり、しかも問題がモデルにないことはよくあります。
- すべての失敗は、harness に構造的欠陥があるというシグナルです。見つけて、直してください。
- 5つの防御レイヤーは、タスク仕様、コンテキスト提供、実行環境、検証フィードバック、状態管理です。医師がまず一般的な原因から除外するように、体系的に確認してください。
- `AGENTS.md` 1つで、より高価なモデルへのアップグレードより効果が出ることがあります。本当です。

## 演習

1. **比較実験**: よく知っているコードベースと、非自明な変更タスクを1つ選んでください。まず harness の支援なしでエージェントを実行し、失敗を記録します。次に、`AGENTS.md` に明示的な検証コマンドを書き加え、同じエージェントで再実行します。各失敗を5つの防御レイヤーのどれかに対応づけながら、結果を比較してください。

2. **verification gap の測定**: 5つのコーディングタスクを選びます。各タスクのあと、エージェントが完了を宣言したかを記録し、その後、独立したテストで実際の正しさを確認します。エージェントが「完了しました」と言ったのに実際は未完了だった割合を数えてください。これがあなたの verification gap です。そのうえで、どの検証コマンドがその割合を下げるか考えてください。

3. **診断ループの練習**: プロジェクト内で、エージェントが安定して失敗するタスクを見つけてください。1回実行して失敗を記録します。それを5つのレイヤーのうち1つに割り当てます。そのレイヤーを修正します。もう一度実行します。これを3〜5回繰り返し、そのたびに改善を記録してください。
