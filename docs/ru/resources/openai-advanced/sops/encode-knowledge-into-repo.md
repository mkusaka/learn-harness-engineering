# SOP: リポジトリに暗黙知を記録する

この SOP は、重要な文脈がまだ Google Docs、チャットのスレッド、チケット、あるいは人の頭の中にしかないときに使ってください。

## 目的

エージェントにとって見えない知識をコードベースの中で見つけられる形にし、以前の会話に頼らなくても、新しいセッションがその知識に基づいて動けるようにすることです。

## トリガーの兆候

- エージェントがシステムの動作を何度も尋ねてくる。
- 人が「それは Slack で決めた」「先週 X が言っていたことに従って」と言う。
- レビューで、リポジトリには存在しない製品ルールやセキュリティルールが参照される。
- 新しいセッションが、本来はもう終わっているはずの発見作業を繰り返している。

## 実行手順

1. 暗黙知の出どころを列挙する。文書、チャット、明文化されていないチームルール、口頭での合意などです。
2. 各出どころについて、それがアーキテクチャか、製品の振る舞いか、セキュリティポリシーか、信頼性に関する期待か、計画の文脈か、参考資料かを確認する。
3. その内容を、適切なリポジトリ内アーティファクトに記録する。
   - アーキテクチャ -> `ARCHITECTURE.md`
   - 製品の振る舞い -> `docs/product-specs/`
   - 設計上の判断理由 -> `docs/design-docs/`
   - 実行状況 -> `docs/exec-plans/`
   - 繰り返し参照される外部リンク -> `docs/references/`
   - 品質や信頼性に関する期待 -> `docs/QUALITY_SCORE.md` または `docs/RELIABILITY.md`
4. 曖昧な表現は、実務で使える具体的な表現に置き換える。
5. 古いコピーを削除するか deprecated と明示し、リポジトリ内に一つの見つけやすい正解だけが残るようにする。

## 良いコーディングの原則

- 文学的に整えるより、見つけやすさを優先する。
- 短く、わかりやすい名前のファイルを優先する。
- 関連するアーティファクト同士を相互にリンクする。
- 会議の書き起こしではなく、長く使うルールを残す。
- 決定が下されたのと同じセッションでリポジトリを更新する。

## 完了条件

- 新しいエージェントが、人に聞かずに必要なルールを見つけられる。
- 同じ事実が、互いに矛盾する複数のファイルに散らばっていない。
- 新しいアーティファクトが、それを管理するコードやプロセスの近くに置かれている。
