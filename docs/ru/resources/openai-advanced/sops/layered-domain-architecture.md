# SOP: 階層型ドメインアーキテクチャ

エージェントが境界を繰り返し破ったり、レイヤー間でロジックを重複させたり、数セッション後にレビューしづらくなるコードを出したりする場合に、この SOP を使ってください。

## 目的

ドメイン境界を十分に明確にし、エージェントが構造を静かに壊すことなく素早く動けるようにします。

## 目標モデル

ビジネスドメイン内では、次の一方向の流れを優先してください。

`Types -> Config -> Repo -> Service -> Runtime -> UI`

横断的な要素は、明示的なプロバイダーまたはアダプターを通して渡す必要があります。
共通ユーティリティはドメインの外に置き、ドメインロジックを溜め込まないようにします。

## 設定チェックリスト

- 現在のドメインを `ARCHITECTURE.md` に定義します。
- 許可される依存方向を `ARCHITECTURE.md` に記録します。
- 横断的インターフェースを固定します: 認証、テレメトリ、外部 API。
- 現在もっとも深刻な境界違反について短いメモを追加します。
- どれをリンター、テスト、またはスクリプトで機械的に検証するかを決めます。

## 実行 SOP

1. 実装スタイルに手を付ける前に、コードベースをドメインごとに区切ります。
2. 各ドメインについて、許可されるレイヤーの順序を定義します。
3. すべての横断的要素を特定し、プロバイダーまたはアダプター経由で通します。
4. あいまいな共通ロジックは、所有ドメインに戻すか、本当に汎用的なユーティリティへ移します。
5. ルールを `ARCHITECTURE.md` に文書化します。
6. 最もコストの高い違反に対して、1つだけ実行可能なガードレールを追加します。
7. 変更後に品質スコアを更新します。

## Definition Of Done

- 新しいエージェントが、その変更がどのレイヤーに属するかを説明できる。
- UI コードがリポジトリや外部副作用に直接触れなくなる。
- 横断的要素に名前付きの入口がある。
- 少なくとも1つの重要な境界が機械的に守られている。

## 更新対象のリポジトリアーティファクト

- `ARCHITECTURE.md`
- `docs/QUALITY_SCORE.md`
- `docs/design-docs/`、根拠となるロジックが変わった場合
- `docs/PLANS.md` またはアクティブな exec plan
