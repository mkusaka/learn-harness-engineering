## レイヤーモデル

エージェントが場当たり的なアーキテクチャをでっち上げないよう、固定された有向モデルを使ってください:

`Types -> Config -> Repo -> Service -> Runtime -> UI`

横断的なエンティティは、明示的なプロバイダーまたはアダプター境界を通して渡すべきであり、
レイヤーをまたいで直接引き回してはいけません。

## 厳格な依存ルール

- 下位層は上位層に依存してはいけません。
- UI はランタイムやサービスの契約を迂回してはいけません。
- データアクセスはリポジトリ、または同等のアダプター経由で行う必要があります。
- 共通ユーティリティは汎用性を保ち、ドメインロジックを抱え込んではいけません。
- 新しい依存関係は、該当する計画書または設計ドキュメントで根拠を示す必要があります。

## 変更チェックリスト

アーキテクチャ上重要なコードを変更するときは:

1. ドメインマップまたは許容される境界が変わった場合は、このファイルを更新してください。
2. 推論ロジックが変わった場合は、`docs/design-docs/` 内の対応する設計ドキュメントを更新してください。
3. ルールを機械的に検証する必要がある場合は、実行可能なチェックを追加または更新してください。
