# AGENTS.md

このリポジトリは、coding-agent が長時間のセッションで作業することを前提にしています。このファイルは短く保ってください。これは巨大な指示の集積ではなく、ドキュメントへのルーティング層、つまり記録システムとして扱ってください。

## 開始時の作業手順

コードを変更する前に、次を行ってください。

1. `pwd` でリポジトリのルートを確認します。
2. 現在のシステムマップと厳格な依存関係ルールを把握するために `ARCHITECTURE.md` を読みます。
3. どのドメインやレイヤーが最も弱いかを確認するために `docs/QUALITY_SCORE.md` を読みます。
4. `docs/PLANS.md` を読み、続けて作業対象のアクティブな plan を開きます。
5. `docs/product-specs/` にある関連する product spec を読みます。
6. このリポジトリの標準的な bootstrap と verification の手順を実行します。
7. 基本の verification が失敗したら、スコープを広げる前にそれを修正します。

## 参照先マップ

- `ARCHITECTURE.md`: ドメインマップ、レイヤーモデル、依存関係ルール
- `docs/design-docs/index.md`: デザイン上の決定と基本方針
- `docs/product-specs/index.md`: 現在の製品挙動と受け入れ基準
- `docs/PLANS.md`: plan のライフサイクルと exec plans の方針
- `docs/QUALITY_SCORE.md`: 製品ドメインとレイヤーの健全性
- `docs/RELIABILITY.md`: ランタイムシグナル、ベンチマーク、再起動に関する期待値
- `docs/SECURITY.md`: シークレット、サンドボックス、データ、外部アクションに関するルール
- `docs/FRONTEND.md`: UI 制約、デザインシステムのルール、アクセシビリティ確認

## 作業上の約束

- 一度に扱うのは、1 つの限定された plan か feature slice にしてください。
- コードを目視で確認しただけで完了扱いにせず、実行可能な証拠を用意してください。
- 挙動を変更した場合は、同じセッション内で該当する product、plan、または reliability のドキュメントを更新してください。
- レビューで同じ指摘が繰り返されるなら、チャットで何度も説明するのではなく、機械的なルール、確認、またはリンターに落とし込んでください。
- 生成物は `docs/generated/` に、元の参照先は `docs/references/` に保管してください。
- このファイルを肥大化させるより、小さくて最新のドキュメントを追加することを優先してください。

## 完了の定義

変更が完了とみなされるのは、次のすべてを満たしたときだけです。

- 対象の挙動が実装されている
- 必要な verification が実際に成功している
- 証拠が該当する plan または quality ドキュメントに添付されている
- 影響を受けたドキュメントが最新の状態である
- リポジトリが標準の開始手順からきれいに再起動できる

## セッション終了時

セッションを終了する前に、次を行ってください。

1. アクティブな exec plan を更新します。
2. あるドメインまたはレイヤーが大きく変わった場合は、`docs/QUALITY_SCORE.md` を更新します。
3. 先送りした新しい技術的負債があれば、`docs/exec-plans/tech-debt-tracker.md` に記録します。
4. 適切であれば、完了した plan を `docs/exec-plans/completed/` に移します。
5. 明確な次の一手が残る、再起動可能な状態でリポジトリを終えてください。
