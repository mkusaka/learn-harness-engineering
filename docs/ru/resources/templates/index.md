# テンプレートガイド

これらのテンプレートは、そのままプロジェクトにコピーして使えるように用意されています。それぞれがエージェントのワークフロー内で特定の役割を持っています。プロジェクトのコマンド、パス、機能名、検証手順に合うように内容を編集してください。

## はじめ方

まず、次の4つのファイルをプロジェクトのルートにコピーしてください。

1. `AGENTS.md` または `CLAUDE.md`
2. `init.sh`
3. `claude-progress.md`
4. `feature_list.json`

プロジェクトの成長に合わせて、他のファイルも追加してください。

---

## AGENTS.md

ルートに置く指示ファイルです。セッション開始時にエージェントが最初に読むファイルでもあります。ここで、コードを書く前に何をするか、どう作業するか、どう終えるかという運用ルールを定めます。

**使い方:**

- プロジェクトのルートディレクトリにコピーする
- スタート時のワークフローの手順を、実際のパスとコマンドに置き換える
- チームの規約に合わせて作業ルールを調整する
- definition of done のセクションは残す。ここが最も重要

**エージェントに対して何をするか:**

- 作業開始前に進捗と機能の状態を読むよう強制する
- 一度に1つの機能だけを扱うよう求める
- 何かを done とマークする前に証拠を求める
- セッションをきれいに終える条件を定義する

`AGENTS.md` は Codex や他のエージェント向けに使います。Claude Code を使う場合は `CLAUDE.md` を使ってください。構成は同じで、Claude の指示スタイルに合わせて整形されているだけです。

## init.sh

開始用スクリプトです。依存関係のインストール、検証、起動コマンドの表示を、1回でまとめて実行します。

**使い方:**

- プロジェクトのルートにコピーする
- 先頭の3つの変数を編集する:
  - `INSTALL_CMD` — 依存関係をインストールするコマンド（例: `npm install`, `pip install -r requirements.txt`）
  - `VERIFY_CMD` — 基本の検証コマンド（例: `npm test`, `pytest`）
  - `START_CMD` — dev サーバーを起動するコマンド（例: `npm run dev`）
- 実行可能にする: `chmod +x init.sh`

**動作:**

1. 現在のディレクトリを表示する（正しい場所で起動しているか確認できるようにするため）
2. 依存関係をインストールする
3. 検証コマンドを実行する
4. 起動コマンドを表示する（`RUN_START_COMMAND=1` が設定されていれば実行もする）

検証に失敗した場合、エージェントはそこで止まり、他の作業をする前に土台を修正しなければなりません。

## claude-progress.md

進捗ログです。各セッションがこのファイルに書き込み、次のセッションは最初にこれを読みます。

**使い方:**

- プロジェクトのルートにコピーする
- 「Current Verified State」セクションを、あなたのプロジェクト情報で埋める
- 各セッションの最後に、そのセッション記録を更新する

**各項目の意味:**

- **Current Verified State** — プロジェクトが今どの状態かを示す唯一の正しい情報源
  - `Repository root directory` — プロジェクトの場所
  - `Standard startup path` — プロジェクトを起動するコマンド
  - `Standard verification path` — テストを実行するコマンド
  - `Highest priority unfinished feature` — 次のセッションが取り組むべき内容
  - `Current blocker` — 停滞している要因すべて
- **Session Record** — セッションごとの記録を1件ずつ残す
  - `Goal` — 何をしようとしていたか
  - `Completed` — 実際に何を完了したか
  - `Verification run` — どのテストを実行したか
  - `Evidence recorded` — どの証拠を残したか
  - `Commits` — 何をコミットしたか
  - `Known risks` — 何が壊れている可能性があるか
  - `Next best action` — 次のセッションが最初に何をすべきか

## feature_list.json

機能トラッカーです。エージェントが実装すべきすべての機能を、状態・検証手順・証拠と一緒に機械可読な形で並べた一覧です。

**使い方:**

- プロジェクトのルートにコピーする
- サンプル機能を自分の機能に置き換える
- 各機能には次が必要:
  - `id` — 短く一意な識別子
  - `priority` — 整数。小さいほど優先度が高い
  - `area` — アプリのどの部分か（例: `"chat"`, `"import"`, `"search"`）
  - `title` — 簡単な説明
  - `user_visible_behavior` — 動作時にユーザーが目にする内容
  - `status` — `not_started`, `in_progress`, `blocked`, `passing` のいずれか
  - `verification` — 動作確認のための手順
  - `evidence` — 検証が通ったことを示す記録（エージェントが埋める）
  - `notes` — 追加の文脈

**ステータスのルール:**

- `not_started` — まだ着手していない
- `in_progress` — 現在作業中の唯一の機能（同時に1つだけ）
- `blocked` — 記録された問題のため継続できない
- `passing` — 検証に合格し、証拠が記録されている

どの時点でも、エージェントが `in_progress` にできる機能は1つだけです。

## session-handoff.md

セッション間で引き継ぐための簡潔なメモです。セッションが終わるとき、次のセッションにすばやく作業を引き継いでほしい場合に使います。

**使い方:**

- プロジェクトのルートにコピーする
- 各セッションの最後に埋める（またはエージェントに埋めさせる）

**各セクションがカバーする内容:**

- **Currently verified** — 何が確認済みで、どの検証を実行したか
- **Changes this session** — コードやインフラで何が変わったか
- **Still broken or unverified** — 既知の問題やリスクの高い箇所
- **Next best action** — 次のセッションが何をすべきか、何を触らないべきか
- **Commands** — 起動・検証・デバッグのコマンドをすぐ参照できる形でまとめる

このファイルは短いセッションでは任意です。セッションが長い場合や、プロジェクトに複数のアクティブ領域がある場合に重要になります。

## clean-state-checklist.md

各セッションの終了前に通すチェックリストです。次のセッションがきれいな状態で始められるよう、リポジトリの状態を保ちます。

**使い方:**

- プロジェクトのルートにコピーする
- セッションを閉じる前に、この項目を確認する
- エージェントも end-of-session ルーティンの一部としてこれらを確認する

**確認内容:**

- 標準の起動手順がまだ動く
- 標準の検証手順がまだ実行できる
- 進捗ログが更新されている
- 機能一覧が実際の状態を反映している（偽の `passing` がない）
- 未記録の中途半端な作業が残っていない
- 次のセッションが手作業の修復なしで続行できる

## evaluator-rubric.md

エージェント出力の品質をレビューするための評価表です。セッション後やプロジェクトのマイルストーンで使い、成果が基準に達しているかを判断します。

**使い方:**

- プロジェクトのルートにコピーする
- セッション後、または複数セッションのまとまりごとに、エージェントの仕事を6つの観点で評価する
- 各観点は 0〜2 点で採点する

**6つの観点:**

1. **Correctness** — 実装は狙いの挙動に一致しているか
2. **Verification** — 必要な確認が証拠付きで本当に実行されているか
3. **Scope discipline** — エージェントは選んだ機能の範囲を守れていたか
4. **Reliability** — 再起動や再実行に耐えられる結果になっているか
5. **Maintainability** — 次のセッションにとってコードとドキュメントが十分わかりやすいか
6. **Handoff readiness** — リポジトリの成果物だけを頼りに、新しいセッションが続けられるか

**判定の選択肢:**

- Accept — 基準を満たしている
- Revise — 受け入れる前に修正が必要
- Block — まず解決すべき根本的な問題がある

**重要: evaluator は調整が必要です。** そのままでは、エージェントは自分自身に甘い判定を出しがちです。問題を見つけたあと、自分で合格を正当化してしまいます。反復して調整してください:

1. 完了したスプリントで evaluator を実行する。
2. その評価を、自分の人間としての判断と比べる。
3. ずれている箇所について、pass/fail の基準をより具体的にする。
4. 再実行して、結果が収束するか確認する。
5. evaluator が人間のレビューと安定して一致するまで繰り返す。

調整には 3〜5 回の反復を見込んでください。収束に何が効いたか追跡できるよう、変更ごとに記録を残してください。

## quality-document.md

プロジェクトの各プロダクト領域と各アーキテクチャ層を評価する品質スナップショットです。個々のセッションの出力だけでなく、コードベース全体の健全性を時間軸で追跡します。

**使い方:**

- プロジェクトのルートにコピーする
- セッション開始前: どこが最も弱いか把握するために読む
- セッション後: 変化に基づいて評価を更新する
- 長期的には: スナップショットを比較し、どの harness 変更がコードベースの健全性を本当に改善したかを見る

**評価対象:**

- **プロダクト領域**（例: ドキュメントのインポート、Q&A フロー、インデックス作成）: 各領域に、検証状態、エージェントにとっての読みやすさ、テストの安定性、主要な欠落をもとに A〜D の評価を付ける
- **アーキテクチャ層**（例: main process, preload, renderer, services）: 各層に、境界の順守状況とエージェントにとっての読みやすさをもとに評価を付ける

**なぜ重要か:**

evaluator のルーブリックはエージェントの個別出力を評価します。quality document はコードベース自体を評価します。答えている問いが違います。

- evaluator ルーブリック: 「このセッションでエージェントはうまく動けたか？」
- quality document: 「プロジェクトは時間とともに強くなっているか、それとも弱くなっているか？」

**更新のタイミング:**

- 重要なセッションのたびに
- ベンチマーク比較の前に
- 整理や単純化の作業の後に
- 新しいエージェントやモデルをプロジェクトに導入するときに

**harness の単純化との関係:**

quality document は、harness の単純化も支えます。harness の各コンポーネントは、モデルがまだできないことについての仮定を表しています。モデルが進化すると、そうした仮定は古くなります。コンポーネントが本当に必要か確かめるには、次の手順を踏みます。

1. quality document のスナップショットを取る。
2. harness のコンポーネントを1つ削除する。
3. ベンチマーク課題のセットを実行する。
4. もう一度スナップショットを取る。
5. 比較する。評価が下がらなければ、そのコンポーネントは不要だったということです。下がったなら、元に戻してください。
