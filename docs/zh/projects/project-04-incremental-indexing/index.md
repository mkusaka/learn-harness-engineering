# Project 04. 実行時フィードバックで agent の挙動を修正する

> 関連講義：[L07. なぜ agent はやりすぎたり、やり切れなかったりするのか](./../../lectures/lecture-07-why-agents-overreach-and-under-finish/index.md) · [L08. なぜ機能一覧が harness の原語なのか](./../../lectures/lecture-08-why-feature-lists-are-harness-primitives/index.md)
> 本編のテンプレートファイル：[templates/](https://github.com/walkinglabs/learn-harness-engineering/blob/main/docs/zh/resources/templates/)

## 何をするか

最初の3つのプロジェクトが重視しているのは、「agent に最後まで仕事をやり切らせること」です。このプロジェクトが扱うのは、「問題が起きたときにどう直すか」 です。しかも、直すのはあなたではなく、実行時シグナルを手がかりに agent 自身が修正します。

やることは2つあります。1つ目は、ナレッジベースアプリに実行時の可観測性を追加することです。起動ログ、取り込みとインデックス作成のログ、Q&A が失敗したときにユーザーへ見えるエラー状態を用意します。2つ目は、agent が黙ってレイヤーをまたいだ違反を起こせないように、リポジトリ内でアーキテクチャ上の制約をコード化することです。対象は `main` / `preload` / `renderer` / `services` の境界です。

その後、コード内に実行時バグを仕込み、agent に修正させます。2回実行します。1回目はログも制約も与えず、agent がどう直すかを見ます。2回目は十分なログとアーキテクチャ規則を与え、違いを比較します。

## 使用するツール

- Claude Code または Codex
- Git
- Node.js + Electron
- ログライブラリ（`electron-log` や簡単な `console` ラッパーなど）
- 構造化チェックツール（ESLint のカスタムルール、guard スクリプト、またはテスト）

## 具体的な手順

### 準備

1. P03 完了後のコードを基点に、同じ commit から作業を始めます。
2. `p04-baseline` と `p04-improved` の2つのブランチを作成します。
3. 両方のブランチに同じ実行時 bug を仕込みます。たとえば、インデックス作成時に chunk サイズの読み取りを誤り、Q&A が空結果を返すようにします。
4. bug の場所と症状は記録しますが、agent には bug の位置を教えません。

### 1回目の実行（弱い harness）

`p04-baseline` ブランチに切り替えます。

1. agent を起動し、「Q&A 機能が空結果を返すので修正してください」と伝えます。
2. リポジトリには実行時ログもアーキテクチャ制約ファイルもありません。
3. agent が根本原因を見つけるまでにかかった時間、修正をどう確認したか、修正中に新しいレイヤー境界違反を持ち込んだかどうかを記録します。
4. 修正後にアプリを再起動し、きれいに起動できるか確認します。

### 2回目の実行（強い harness）

`p04-improved` ブランチに切り替えます。agent を起動する前に、まずリポジトリ内で以下を準備します。

- **実行時ログ**: 起動時に初期化手順を出力し、取り込み時にファイル数と chunk 結果を出力し、インデックス作成時に進捗を出力し、Q&A 失敗時にエラー原因を出力します。
- **アーキテクチャ制約**: `AGENTS.md` に Electron の4層境界（`main` / `preload` / `renderer` / `services`）を明記し、どの呼び出し経路が許可されるかを説明します。違反は ESLint ルールまたは guard スクリプトで検査します。
- **クリーンな状態の要件**: 最終納品前に、必ずきれいに再起動できること。

そのうえで agent を起動します。

1. まず、agent にログと構造化チェックを追加させます。これはタスクの一部です。
2. その後、「Q&A 機能が空結果を返すので修正してください」と伝えます。
3. 今回は agent が参照できるログがあり、頼れるアーキテクチャ規則もあります。
4. 診断速度、修正品質、境界違反を持ち込んだかどうかを記録します。
5. 修正後にアプリを再起動し、クリーンに起動できることを確認します。

## 結果の測り方

| 指標 | 説明 |
|------|------|
| 根本原因の特定時間 | 開始してから agent が bug の原因を正確に説明するまでの時間 |
| 修正確認時間 | 原因特定から、修正が成功したことを検証するまでの時間 |
| 境界違反数 | 修正中に持ち込まれたレイヤーをまたいだ違反の回数 |
| ログの有用性 | ログが失敗原因を直接示しているか |
| クリーン再起動 | 修正後にエラーなくクリーンに再起動できるか |

## 提出物

- 弱い harness のデバッグ記録: 診断プロセス、修正 diff、起動証拠
- 強い harness のデバッグ記録: 上記に加えて、ログとアーキテクチャ制約ファイル
- 構造化チェックの成果物（lint ルール、guard スクリプト、またはテストファイル）
- 比較ノート: 診断速度と修正の堅牢性を重点的に比較したもの
