# Project 05. agent に自分の実装を自己検証させる

> 関連講義：[L09. なぜ agent は勝利宣言を早まるのか](./../../lectures/lecture-09-why-agents-declare-victory-too-early/index.md) · [L10. なぜ end-to-end テストは結果を変えるのか](./../../lectures/lecture-10-why-end-to-end-testing-changes-results/index.md)
> 本篇テンプレートファイル：[templates/](https://github.com/walkinglabs/learn-harness-engineering/blob/main/docs/zh/resources/templates/)

## 何をするのか

前四つのプロジェクトでは、「ちゃんとできているかを確認する」作業は、あなたが手動で行うか、ファイル規則によって強制されていました。このプロジェクトでは、agent 自身にそれを確認させます。

方法は役割分離です。これまでは同じ agent がコードを書き、品質も判断していました。今回はそれを分けます。ひとつの agent が実装を担当し（生成者）、別の agent がレビューを担当します（評価者）。さらにもうひとつ、計画を担当する役割（計画者）も追加できます。これを三回実行し、役割分離を一段ずつ増やすことで結果がどれだけ良くなるかを確認します。

実質的な機能改善をひとつ選びます。たとえば、複数ターンの会話履歴、引用パネルの再設計、ドキュメント集合とフィルタリングなどです。三回とも同じ機能改善を行い、変えるのは harness の役割分担だけにします。

## 使うツール

- Claude Code または Codex（生成者役と計画者役に使用）
- 同じ、または別の agent インスタンス（評価者役に使用）
- 評価ルーブリック（`docs/zh/resources/templates/evaluator-rubric.md` を参照）
- Sprint contract テンプレート（`docs/lectures/lecture-11-why-observability-belongs-inside-the-harness/code/sprint-contract.md` を参照）

## 具体的な手順

### 準備作業

1. P04 完了後のコードを基点に、同じ commit から始めます。
2. `p05-single`、`p05-gen-eval`、`p05-plan-gen-eval` の 3 つの branch を作成します。
3. 実施する機能改善を 1 つ決め、受け入れ基準を明文化します。3 回の実行で、機能の範囲と受け入れ基準は完全に同一にします。
4. 評価ルーブリックを作成し、採点項目には少なくとも正確性、信頼性、保守性、ユーザー体験を含めます。

### 1 回目の実行（弱い harness - 単一役割）

`p05-single` branch に切り替えます。

1. 1 つの agent が計画、実装、自分での確認までをすべて担当します。
2. 外部の評価ルーブリックは使わず、agent 自身が出来栄えを判断します。
3. 最終成果物と未解決の不具合を記録します。

### 2 回目の実行（強い harness - 生成者 + 評価者）

`p05-gen-eval` branch に切り替えます。

1. 生成者と評価者はまず sprint contract で認識をそろえます。何をするか、どう検証するか、何が範囲外かを明確にします。
2. 生成者が機能を実装します。
3. 評価者が評価ルーブリックで採点し、問題点をフィードバックします。
4. 生成者がフィードバックを反映して修正します。少なくとも 1 回は修正版を作ります。
5. 評価者が見つけた不具合の数と、修正した内容の量を記録します。

### 3 回目の実行（さらに強い harness - 計画者 + 生成者 + 評価者）

`p05-plan-gen-eval` branch に切り替えます。

1. 計画者がまずタスクを分解し、手順と依存関係を定義します。
2. 生成者がその計画に従って実装します。
3. 評価者が同じ評価ルーブリックで採点します。
4. 少なくとも 1 回は修正を行います。
5. 計画によって手戻りが減ったかを記録します。

### 評価者のチューニング

評価者は一度で十分に使えるとは限りません。初期版の評価者は、問題を見つけたあとで「やはり通してよい」と自分を納得させてしまいがちです。そこで次の作業が必要です。

1. 完了済みの sprint を、評価者に採点させます。
2. あなた自身の判断と比較します。
3. 食い違う箇所があれば、ルーブリックをより具体的にします。
4. 評価者を再実行し、どれだけ揃ったかを確認します。
5. 3-5 を繰り返し、評価者の判断があなたの判断とほぼ一致するまで続けます。各回のチューニング内容を記録します。

## 結果の測り方

| 指標 | 説明 |
|------|------|
| 範囲定義の質 | コーディング前のタスク分解の明確さ |
| 不具合検出数 | 受け渡し前に評価者が見つけた不具合の数と重大度 |
| ルーブリックの採点 | 各観点の得点（正確性、信頼性、保守性、UX） |
| 手戻り量 | 評価フィードバック後にやり直しが必要だった割合 |
| 最終的な堅牢性 | 改善後の機能が実運用でどれだけ安定しているか |
| 評価者のチューニング回数 | 評価者の判断をあなたに合わせるまでの反復回数 |
| Sprint contract の効果 | 評価時の曖昧さをどれだけ減らせたか |

## 提出物

- Sprint contract 文書
- 評価者のチューニングログ（各回で何を変えたか、その理由）
- 単一役割での実行記録：プロンプト、ログ、実行可能な証拠
- 生成者 + 評価者での実行記録：ルーブリックの採点と修正記録を含む
- 計画者 + 生成者 + 評価者での実行記録：計画文書、ルーブリックの採点、修正記録を含む
- 比較メモ：品質向上の幅と調整コスト
