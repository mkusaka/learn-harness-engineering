# テンプレート利用ガイド

これらのテンプレートは、そのままプロジェクトにコピーして使えます。各ファイルは agent のワークフローの中でそれぞれ役割があります。コピーしたら、中にあるコマンド、パス、機能名、検証手順を自分のプロジェクトに合わせて置き換えてください。

## 始め方

まず、この 4 つのファイルをプロジェクトのルートにコピーします。

1. `AGENTS.md` または `CLAUDE.md`
2. `init.sh`
3. `claude-progress.md`
4. `feature_list.json`

プロジェクトが複雑になってきたら、残りのファイルを追加してください。

---

## AGENTS.md

ルート指示ファイルです。agent は毎回最初にこのファイルを読みます。ここでは、作業を始める前に何をするか、作業中にどう規律を守るか、最後に何を確認するかといったルールを定義します。

**使い方：**

- プロジェクトのルートにコピーする
- 開始手順の中にあるステップを、自分のプロジェクトのパスとコマンドに置き換える
- ワークルールはチームの約束に合わせて調整する
- 完了条件の部分は変えないこと。それがこの harness の最重要部分です

**agent がこれでできること：**

- 作業開始前に進捗と機能の状態を読むよう促す
- 一度に 1 つの機能だけに集中させる
- 完了判定に証拠を求める
- 「きれいに終わった」と言える状態の定義を与える

`AGENTS.md` は Codex や他の agent 向けに使います。`CLAUDE.md` は Claude Code 向けです。中身は同じで、Claude の指示スタイルに合わせたフォーマットになっています。

## init.sh

起動スクリプトです。依存関係のインストール、検証、起動コマンドの表示を 1 回で済ませます。

**使い方：**

- プロジェクトのルートにコピーする
- 先頭の 3 つの変数を変更する
  - `INSTALL_CMD` — 依存関係のインストールコマンド（たとえば `npm install`、`pip install -r requirements.txt`）
  - `VERIFY_CMD` — 基本検証コマンド（たとえば `npm test`、`pytest`）
  - `START_CMD` — 開発サーバーの起動コマンド（たとえば `npm run dev`）
- 実行権限を付ける：`chmod +x init.sh`

**やること：**

1. 現在のディレクトリを表示する（正しい場所で実行されていることを確認する）
2. 依存関係をインストールする
3. 検証コマンドを実行する
4. 起動コマンドを表示する（`RUN_START_COMMAND=1` が設定されていれば、そのまま起動する）

検証に失敗したら、agent は止まって基礎状態を先に直すべきです。壊れた土台の上に新機能を積み重ねてはいけません。

## claude-progress.md

進捗ログです。会話のたびに書き込み、次の新しい会話では最初に読みます。

**使い方：**

- プロジェクトのルートにコピーする
- 「現在の検証済み状態」の欄にプロジェクト情報を埋める
- 各会話の終わりに会話記録を更新する

**各フィールドの意味：**

- **現在の検証済み状態** — プロジェクトの今の進捗を示す唯一の真実
  - `リポジトリのルート` — プロジェクトの場所
  - `標準起動パス` — プロジェクトを立ち上げるコマンド
  - `標準検証パス` — テストを実行するコマンド
  - `現在の最優先未完了機能` — 次の会話で取り組むべきこと
  - `現在の blocker` — 何が詰まっているか
- **会話記録** — 会話ごとに 1 件ずつ
  - `今回の目標` — 何をやるつもりか
  - `完了したこと` — 実際にやったこと
  - `実行した検証` — 何のテストを走らせたか
  - `記録した証拠` — どんな証拠を残したか
  - `コミット記録` — どんな commit を作ったか
  - `既知のリスクまたは未解決の問題` — どこに問題の可能性があるか
  - `次の最善手` — 次の会話の開始地点

## feature_list.json

機能一覧です。機械可読な機能リストで、各機能には状態、検証手順、証拠があります。

**使い方：**

- プロジェクトのルートにコピーする
- サンプル機能を自分のものに置き換える
- 各機能には次を埋める
  - `id` — 短くて一意な識別子
  - `priority` — 整数。小さいほど優先度が高い
  - `area` — アプリのどの領域か（たとえば "chat"、"import"、"search"）
  - `title` — 簡単な説明
  - `user_visible_behavior` — 正常時にユーザーから見える挙動
  - `status` — 4 つの状態のいずれか：`not_started`、`in_progress`、`blocked`、`passing`
  - `verification` — 手順ごとの検証ステップ
  - `evidence` — 検証に通った記録（agent が記入）
  - `notes` — 補足説明

**状態ルール：**

- `not_started` — まだ手を付けていない
- `in_progress` — 現在取り組んでいるもの（同時に 1 つだけ）
- `blocked` — 記録された阻害要因があり、進められない
- `passing` — 検証に合格し、証拠が記録済み

agent は、いつでも `in_progress` の機能を 1 つだけ持てます。

## session-handoff.md

会話の引き継ぎ要約です。1 回の会話が終わるときに書き、次の会話の開始時に読みます。引き継ぐ人（または agent）が現状をすばやく把握できるようにします。

**使い方：**

- プロジェクトのルートにコピーする
- 各会話の終わりに記入する（agent 自身に書かせてもよい）

**各セクションに書く内容：**

- **現在の検証済み内容** — 何が動くと確認できているか、どんな検証をしたか
- **今回の変更** — どのコードや基盤を変えたか
- **まだ壊れているもの / 未検証のもの** — 既知の問題やリスク領域
- **次の最善手** — 次の会話で何をするべきか、何を触らないべきか
- **コマンド** — 起動、検証、デバッグの各コマンド。すぐ参照できるようにする

短い会話なら、このファイルは省略してもかまいません。会話が長くなる場合や、複数の領域が並行しているプロジェクトでは、とても重要になります。

## clean-state-checklist.md

締めの確認チェックリストです。毎回の会話の終わりにこれを確認し、リポジトリが次の会話でそのまま着手できる状態になっていることを確かめます。

**使い方：**

- プロジェクトのルートにコピーする
- 会話を閉じる前に項目ごとに確認する
- agent の終了手順にもこれらの確認を含めるべきです

**確認すること：**

- 標準起動パスがまだ使える
- 標準検証がまだ実行できる
- 進捗ログが更新済み
- 機能一覧が passing と未検証の境界を正しく反映している（偽の passing がない）
- 記録されていない半端な作業が残っていない
- 次の会話が人手で修復しなくても続けられる

## evaluator-rubric.md

レビュー採点表です。会話の終わりやマイルストーン到達時に、agent の成果が基準に達しているかを評価します。

**使い方：**

- プロジェクトのルートにコピーする
- 1 回、または複数回の会話の後で、6 つの観点それぞれを採点する
- 各観点は 0〜2 点

**6 つの観点：**

1. **正確性** — 実装された挙動が、目標の機能に一致しているか
2. **検証** — 求められた確認を本当に実行し、証拠を残しているか
3. **範囲の規律** — 選んだ機能の範囲から大きく外れていないか
4. **信頼性** — 再起動や再実行後も同じように動くか
5. **保守性** — 次の会話に渡しても理解できる程度に、コードと文書が明確か
6. **引き継ぎ準備度** — 新しい会話がリポジトリ内のファイルだけで続行できるか

**結論の選択肢：**

- Accept — 合格
- Revise — 受け入れるには修正が必要
- Block — 根本的な問題があり、先に解消が必要

**Evaluator は調整が必要です。** 初期状態の agent によるレビューは弱く、問題を見つけても、自分で自分を説得して合格にしてしまいがちです。何度も調整してください。

1. evaluator で、完了済みの sprint を 1 つ採点する。
2. そのスコアを自分の手動判断と比べる。
3. 食い違う部分は、rubric の合格・不合格基準をもっと具体的に書く。
4. 同じ出力に対して evaluator を再実行し、ずれが解消したか確認する。
5. evaluator の判断が手動レビューとおおむね一致するまで繰り返す。

校正には 3〜5 回かかる見込みです。各回で、何をどう変えたか、なぜ変えたかを記録してください。

## quality-document.md

品質スナップショットです。プロジェクトの各製品領域とアーキテクチャ層を採点し、コードベースが時間とともに強くなっているか弱くなっているかを追跡します。

**使い方：**

- プロジェクトのルートにコピーする
- 会話の開始前に読む。コードベースのどこが最も弱いかを把握するため
- 会話の終了後に評価を更新する
- 長期的には、異なる時点のスナップショットを比べて、どの harness 変更がコードベースの健全性を本当に改善したかを見る

**何を評価するか：**

- **製品領域**（たとえば文書インポート、Q&A フロー、インデックス）：各領域を、検証状態、Agent にとっての読みやすさ、テストの安定性、重要な欠落で採点する
- **アーキテクチャ層**（たとえば Main Process、Preload、Renderer、Services）：各層を、境界の実行と Agent にとっての読みやすさで採点する

**なぜ必要か：**

Evaluator rubric は、単発の agent 出力の品質を評価します。Quality document は、コードベースそのものの品質を評価します。答えている問いが違います。

- Evaluator rubric: "この回の agent はよくやったか？"
- Quality document: "このプロジェクトは強くなっているか、弱くなっているか？"

**いつ更新するか：**

- 重要な会話が終わるたび
- ベースライン比較の前
- 整理や単純化の後
- 新しい agent や新しいモデルに切り替えるとき

**harness の簡素化との関係：**

Quality document は、harness を簡素化できるかどうかの検証にも使えます。harness の各コンポーネントには、「モデルにはこれができない」という仮説が埋め込まれています。モデルが強くなれば、その仮説は古くなります。あるコンポーネントがまだ必要かどうかを確認するには、次のようにします。

1. quality document のスナップショットを 1 つ取る。
2. harness のコンポーネントを 1 つ外す。
3. ベンチマークを実行する。
4. もう 1 つスナップショットを取る。
5. 比較する。評価が下がっていなければ、そのコンポーネントは不要だということです。下がったなら、元に戻します。
