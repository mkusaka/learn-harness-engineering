## レイヤーモデル

固定方向のレイヤーモデルを使い、agent がその場で架空のアーキテクチャを作らないようにします。

`Types -> Config -> Repo -> Service -> Runtime -> UI`

ドメイン横断の関心事は、明示された provider か adapter の境界を通して入れるべきであり、レイヤーを直接またいで透過させてはいけません。

## 厳格な依存ルール

- 下位層は上位層に依存してはいけません。
- UI は runtime や service の契約を迂回してはいけません。
- データアクセスは必ず repo か同等の adapter を通してください。
- 共有 util は汎用性を保ち、じわじわとドメインロジックのゴミ箱にならないようにしてください。
- 新しい依存関係は、対応する plan か design doc で理由を説明してください。

## 変更チェック

アーキテクチャに影響するコードを変更したときは、次の対応を行ってください。

1. ドメインマップや許容境界が変わったら、このファイルを更新する。
2. 背後にある設計上の理由が変わったら、`docs/design-docs/` の関連文書を更新する。
3. ルールを機械的に適用すべきなら、実行可能なチェックを追加する。
