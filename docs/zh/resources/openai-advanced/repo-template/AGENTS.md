# AGENTS.md

このリポジトリは、長時間稼働する coding-agent のワークフロー向けです。このファイルは簡潔に保ち、「唯一の事実源」文書への入口と振り分け役として扱ってください。肥大化した詳細説明書にしないでください。

## 開始手順

コードを変更する前に、次の手順を実施してください。

1. `pwd` でリポジトリのルートを確認する。
2. `ARCHITECTURE.md` を読み、現在のシステム全体図と必須の依存ルールを把握する。
3. `docs/QUALITY_SCORE.md` を読み、もっとも弱い製品領域とアーキテクチャ層を先に把握する。
4. `docs/PLANS.md` を読み、その後で実行対象の active plan を開く。
5. 関連する `docs/product-specs/` の仕様文書を読む。
6. このリポジトリで定められた bootstrap と検証の手順を実行する。
7. 基本検証が先に失敗した場合は、まず baseline を修正してから新しい範囲に進む。

## 参照マップ

- `ARCHITECTURE.md`：領域マップ、レイヤーモデル、依存ルール
- `docs/design-docs/index.md`：設計判断と中核となる考え方
- `docs/product-specs/index.md`：現在の製品挙動と受け入れ目標
- `docs/PLANS.md`：計画のライフサイクルと実行計画ルール
- `docs/QUALITY_SCORE.md`：製品領域とアーキテクチャ層の健全性
- `docs/RELIABILITY.md`：稼働シグナル、benchmark、再起動要件
- `docs/SECURITY.md`：秘密情報、サンドボックス、データ、外部アクションのルール
- `docs/FRONTEND.md`：UI 制約、デザインシステム規則、アクセシビリティ確認

## 作業ルール

- 一度に扱うのは、境界の明確な 1 つの計画か機能スライスだけにする。
- コードを読むだけで完了と判断してはいけない。必ず実行可能な証拠を残すこと。
- 挙動を変更した場合は、対応する製品文書、計画文書、または信頼性文書も同時に更新する。
- ある種の review feedback が繰り返し出るなら、口頭で何度も説明するのではなく、機械的なルール、チェック、または linter に昇格させる。
- 生成物は `docs/generated/` に置き、外部参照は `docs/references/` に置く。
- さらに詳細が必要なら、このファイルを長くするのではなく、小さく新しい文書を追加することを優先する。

## 完了条件

次の条件がすべて満たされて初めて、変更は完了とみなします。

- 目的の挙動が実装されている
- 要求された検証を実際に実行した
- 証拠が関連する plan または quality 文書に紐づいている
- 影響を受けた文書が最新の状態である
- リポジトリが標準の起動手順でクリーンに再起動できる

## 仕上げ

セッションを終了する前に、次を実施してください。

1. 現在の active execution plan を更新する。
2. 製品領域またはアーキテクチャ層に明確な変更がある場合は、`docs/QUALITY_SCORE.md` を更新する。
3. 後回しにする技術的負債があれば、`docs/exec-plans/tech-debt-tracker.md` に記録する。
4. 完了した plan は、速やかに `docs/exec-plans/completed/` へ移す。
5. リポジトリが再起動可能であることを保証し、次の明確なアクションを残す。
