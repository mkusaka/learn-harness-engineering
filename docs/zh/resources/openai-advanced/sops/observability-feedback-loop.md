# SOP：可観測性フィードバックループ

デバッグに時間がかかりすぎるとき、agent が証拠もなく成功を宣言しがちなとき、あるいは実行時の挙動のほうがコード自体よりも理解しづらいときは、この SOP を使います。

## 目的

agent にローカルで完結するループを与え、logs、metrics、traces、そして再現可能な workload をもとにシステムを判断できるようにします。コードを眺めて推測するのではありません。

## 最小可用スタック

- アプリが構造化ログを出力する
- 条件が許せば metrics と traces を出力する
- ローカル収集層または fan-out 層
- logs / metrics / traces を問い合わせられるインターフェース
- 変更のたびに再実行できる workload または user journey

## SOP の実行

1. まず最も重要な golden な実行経路を定義する。
2. 起動フローと主要経路に構造化ログを追加する。
3. 適切な場所に latency、failure count、queue depth などの metrics を追加する。
4. 遅い経路や複数段階のフローに traces または timing マーカーを追加する。
5. これらのシグナルをローカル開発環境から問い合わせ可能にする。
6. agent に、繰り返し再実行できる workload またはシナリオを与える。
7. 次のループを強制する: query -> correlate -> reason -> implement -> restart
   -> rerun -> verify。

## デバッグセッションのチェックリスト

- どこで失敗しているのか？
- 失敗を証明できるシグナルはどれか？
- 失敗はどの層に属するのか？
- 修正後、どのシグナルが変化したか？
- App はクリーンに再起動できるか？
- 同じ workload を再実行したときに通るか？

## 完了条件

- agent が実行証拠を使って失敗パターンを説明できる。
- 変更のたびに同じ workload を再実行できる。
- restart と rerun が通常のタスク循環の一部になっている。
- 信頼性のシグナルが `docs/RELIABILITY.md` に記録されている。
