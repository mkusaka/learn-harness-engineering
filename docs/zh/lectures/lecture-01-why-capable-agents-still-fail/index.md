# 第一講. モデル能力が高いことと、実行が信頼できることは別

あなたもなかなか場数を踏んできたつもりでしょう。Claude Pro は契約済みで、GPT-4o の API key もある。SWE-bench のランキングの数字だって、誰よりも気にして見ている。ある日ついに、AI agent に本物のプロジェクトを任せようと思い、自信満々に指示を出す。結果はどうか。機能は追加されたのにテストは落ちる、バグは直したのに新しいバグを生む、20 分走らせてから自信満々に「完了しました」と言う。ところがコードを見れば、まったく求めていたものではない。

そのとき、最初に浮かぶのは何でしょうか。「このモデルはダメだ。もっと高いのに替えよう」でしょうか。少し待ってください。財布を開く前に、問題が本当にモデル側にあるのかを疑うべきです。

まずはデータを見ましょう。ベンチマークの数字は変化が速い。Anthropic は 2025 年 9 月に、Claude Sonnet 4.5 が SWE-bench Verified で 77.2% に達したと発表しました。つまり、モデルがベンチマークで強く見えても、それはよく選別された、明確な issue の説明とテストケースがあるタスクでの結果にすぎません。日々の開発、つまり要件があいまいで、既成のテストがなく、暗黙の業務ルールがあちこちに散らばっている環境に持ち込むと、この数字はそのまま再現されません。

しかし、このデータの背後には、直感に反する事実が隠れています。

## 同じ馬、2つの運命

Anthropic は対照実験を行いました。同じ prompt（"2D のレトロゲームエディタを作る"）、同じモデル（Opus 4.5）です。1 回目は何も付けずに動かしてみたところ、20 分かかって $9 を使い、ゲームの核となる機能はまったく動きませんでした。2 回目は完全な harness（planner + generator + evaluator の 3 agent 構成）を付けたところ、6 時間かかって $200 を使いましたが、ゲームは普通に遊べるところまで到達しました。

モデルは変えていません。Opus 4.5 は相変わらず Opus 4.5 です。変わったのは鞍でした。

OpenAI が 2026 年に公開した harness engineering の記事では、もっと率直にこう述べています。Codex は、harness がよく組まれたリポジトリでは、"信頼できない" 状態から "信頼できる" 状態へ変わりうる。注目すべきは言葉の選び方です。単に「少し良くなった」のではなく、性質が変わるということです。名馬も鞍がなければ乗れますが、長くは走れないし、速くも走れないし、落馬しても不思議ではない。harness はその鞍です。つまり、**モデル重み以外のすべてのエンジニアリング基盤**です。

## agent はどこで詰まるのか

では、具体的には何が問題なのでしょうか。

最もよくあるのは、そもそもタスクの伝え方が曖昧なことです。「検索機能を追加して」と言っても、agent の理解はあなたとまったく一致していないかもしれません。何を検索するのか。全文検索か、構造化検索か。ページネーションは必要か。ハイライトは要るのか。そこを説明していないと、agent は勝手に推測します。当たれば運、外れれば後から修正することになり、その修正コストは最初に明確に伝えるより高くつくこともある。これは、店で「魚をください」とだけ言って、焼き魚が出るのか煮魚が出るのか蒸し魚が出るのか、運任せにするようなものです。

たとえ説明が十分でも、プロジェクト内の暗黙の設計ルールは agent には分かりません。チームでは SQLAlchemy 2.0 の新しい書き方を標準にしているのに、agent は 1.x のコードを書いてしまう。すべての API エンドポイントは OAuth 2.0 認証を通す必要があるのに、そのルールはあなたの頭の中と、3 か月前の Slack メッセージの中にしかない。Agent には見えないのです。従う気がないのではなく、そもそも存在を知らないのです。

環境も落とし穴です。開発環境のセットアップが不完全、依存関係が足りない、ツールのバージョンが合っていない。Agent は貴重なコンテキストウィンドウを、`pip install` の失敗や Node のバージョン不一致のような問題に費やしてしまい、本来のタスクに集中できません。木工職人を呼んだのに、ハンマーがない、釘が見つからない、作業台まで傾いているようなものです。腕がよくても力を発揮できません。

さらに多いのが、検証手段そのものがないことです。テストがない、lint がない、あるいは検証コマンドを agent に伝えていない。Agent はコードを書き終えると、自分で見て「問題なさそうです」と言って完了扱いにします。答案の照合方法を与えずに学生に宿題を出すようなものです。本人は正しく解けたつもりでも、採点すると誤りだらけということが起きる。Anthropic は、agent がコンテキストの残りが少ないと感じると、今やっている作業を急いで切り上げ、検証を飛ばし、最適ではなく単純な解決策を選びがちだという興味深い現象も観測しています。彼らはこれを「context anxiety」と呼びました。試験時間が迫ってきて、選択肢を適当に埋めるのに似ています。

長時間タスクを会話セッションをまたいで進めると、状況はさらに悪化します。前回の会話で得た発見が失われ、毎回の新しいセッションでプロジェクト構造やコードの整理方法を最初から探り直さなければならない。状態を保持できない agent は、30 分を超えるタスクで失敗率が急激に上がります。

## 重要用語

上の状況を理解すると、これらの概念はただの用語ではなくなります。

- **Capability Gap**：モデルのベンチマーク上の成績と、実際のタスクでの成績との差が大きいこと。SWE-bench Verified の通過率が高くても、実際の issue は要件のあいまいさ、暗黙の設計ルール、検証不足によってずっと難しくなります。
- **Harness**：モデル以外のすべてです。指示、ツール、環境、状態管理、検証フィードバック。モデル重み以外の部分はすべて harness です。つまり、ここで言う「鞍」です。
- **Harness 由来の失敗**：モデル自体の能力は十分でも、実行環境に構造的な欠陥があるために失敗すること。Anthropic の対照実験がその例です。
- **検証ギャップ**：agent の出力に対する自己評価と、実際の正しさとのずれです。agent が「終わりました」と言っているのに実際は終わっていない。これが最もよくある失敗パターンです。
- **診断ループ**：実行 → 失敗の観測 → harness のどの層に問題があるかを特定 → その層を修正 → 再実行。これが harness engineering の中心的な方法論です。
- **完了条件（Definition of Done）**：コマンドで検証できる条件の集合です。テストが通る、lint にエラーが出ない、型チェックが通る。明示的な完了条件がなければ、agent は自分で作り話をしてしまいます。

## 失敗したら、まず harness を直す

基本原則はこうです。**失敗したら、まずモデルを替えるのではなく、harness を確認する。** 同じモデルが、似たような構造の整ったタスクでは成功するなら、まず疑うべきは harness です。車が止まったときに、最初からエンジン故障を疑わず、まずガソリン切れを確認するのと同じです。

具体的には次のとおりです。

**失敗のたびに、どの層で起きたのかを特定する。** ただ「モデルがダメだった」と言うのではなく、タスクの説明が不十分だったのか、コンテキストが足りなかったのか、検証手段がなかったのかを問います。すべての失敗を、5 層の防御（タスク仕様、コンテキスト供給、実行環境、検証フィードバック、状態管理）のどれかに帰属させてください。この習慣がつくと、「モデルがダメ」という結論がログに出てくる回数はどんどん減っていきます。

**すべてのタスクに明示的な完了条件を書く。** 「検索機能を追加して」ではなく、次のように書きます。
```
完了条件：
- GET /api/search?q=xxx エンドポイントを追加する
- ページネーションをサポートし、デフォルトは 20 件にする
- 結果にハイライト片を含める
- すべての新規コードが pytest を通る
- 型チェックが通る（mypy --strict）
```

**AGENTS.md ファイルを作る。** リポジトリのルートに、そのプロジェクトの技術スタック、設計上の約束事、検証コマンドを agent に伝えるファイルを置きます。これが harness engineering の第一歩であり、費用対効果が最も高い一歩でもあります。`AGENTS.md` 1 つで、より高価なモデルに替えるより効果が出ることがあります。本気です。

**診断ループを回す。** 失敗を「またモデルが変なことをした」と捉えず、「harness に新しい欠陥が見つかった」というサインとして扱います。失敗ごとに、どの層で起きたかを特定し、修正し、次回は同じ失敗を起こさないようにする。数回まわすうちに harness は強くなり、agent の挙動は安定して改善します。道路工事と同じで、穴を 1 つ埋めるたびに次の区間は平らになります。

**改善を定量化する。** 簡単なログを残しましょう。各タスクが成功したかどうか、失敗したならどの層の問題だったか。数回回すと、どの層がボトルネックかが見えてきます。そこに集中して手を入れればよいのです。

## 100 万行コードの実験

OpenAI が 2026 年に公開した記事では、2025 年後半から始まった大胆な実験が紹介されています。Codex を使い、空の git リポジトリからスタートして、完全な社内プロダクトを構築したのです。5 か月後、そのリポジトリにはおよそ 100 万行のコードがありました。アプリケーションロジック、インフラ、ツール、ドキュメント、社内開発ツールまで、すべて agent が生成しました。3 人のエンジニアが Codex を動かし、約 1,500 件の PR を作成してマージしました。平均すると 1 人あたり 1 日 3.5 件の PR です。

この実験の重要な制約は、**人間が直接コードを書かないこと** でした。これは見せかけではなく、チームに次の点をはっきりさせるためです。エンジニアの主な仕事がコードを書くことではなく、環境を設計し、意図を表現し、フィードバックループを構築することになったとき、何が本当に変わるのか。

初期の進みは予想より遅いものでした。Codex が弱かったのではなく、環境が十分ではなかったのです。agent が高次の目標を進めるのに必要なツール、抽象化、内部構造が不足していました。エンジニアの仕事は、大きな目標を小さなブロック（設計、コーディング、レビュー、テスト）に分解し、それを agent に組み立てさせ、そのブロックを使ってさらに複雑なタスクを解放していくことへ変わりました。何かが失敗したとき、修正はたいてい「もっと頑張る」ではなく、「agent に何が足りないのか、それをどうすれば理解可能で実行可能な形にできるのか」でした。

この実験は、本講の核心的な主張を直接裏づけています。**同じモデルでも、何もない環境と、完全な harness がある環境では、出力が本質的に変わる。** モデルは変わっていません。変わったのは環境です。

> 出典：[OpenAI: Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)

## もっと身近な例

あるチームは、Claude Sonnet を使って中規模の Python Web アプリケーション（FastAPI + PostgreSQL + Redis、約 15,000 行のコード）に新しい API エンドポイントを追加しました。

最初は一文だけを渡しました。「`/api/v2/users` の下にユーザー設定エンドポイントを追加する」。結果はどうだったか。agent はコンテキストウィンドウの 40% を使ってリポジトリ構造の探索に費やし、一見もっともらしいコードを出しましたが、プロジェクトのエラーハンドリング規約に従わず、古い SQLAlchemy の文法を使い、完了したと主張したものの、実際のエンドポイントには実行時エラーがありました。次のセッションでは、また最初から探索し直す必要がありました。

その後、`AGENTS.md`（プロジェクトのアーキテクチャと技術スタックのバージョンを記載）、明示的な検証コマンド（`pytest tests/api/v2/ && python -m mypy src/`）、アーキテクチャ決定記録を追加しました。同じモデルは 3 回の独立した実行で全て成功し、コンテキストの使用効率は約 60% 向上しました。

モデルは変わっていません。やはり変わったのは harness です。

## 持ち帰るもの

- モデルの能力と、実行の信頼性は別物です。名馬にも、ちゃんとした鞍が必要です。
- 失敗したら、まず harness を見て、それからモデルを見ます。モデルを替えるのは最もコストの高い選択であり、しかも多くの場合、そもそもモデルの問題ではありません。
- 失敗はすべて、harness に構造的な欠陥があるというサインです。それを見つけて、直してください。
- 5 層の防御: タスク仕様、コンテキスト供給、実行環境、検証フィードバック、状態管理。順に切り分けていけば、医者がまずよくある病因から調べるのと同じです。
- `AGENTS.md` 1 つで、より高価なモデルに替えるより効果が出ることがあります。本当にそうです。

## 練習

1. **比較実験**：よく知っているコードベースと、単純ではない変更タスクを 1 つ選びます。まずは harness の支援なしで agent を 1 回走らせ、失敗を記録します。次に `AGENTS.md` と明示的な検証コマンドを追加し、同じ agent でもう 1 回走らせます。2 回の結果を比較し、失敗を 5 層の防御のどれかに帰属させてください。

2. **検証ギャップの測定**：5 つのコーディングタスクを選び、各タスクの完了後に agent が完了を主張したかどうかを記録します。そのうえで、独立したテストで実際の正しさを確認します。実際には終わっていないのに終わったと主張した割合を計算してください。これがあなたの検証ギャップです。次に、どの検証コマンドを追加すればこの割合を下げられるか考えてみましょう。

3. **診断ループの実践**：あなたのプロジェクトで agent が繰り返し失敗するタスクを 1 つ見つけます。1 回実行して、失敗を記録します。5 層のうちどこが原因かを特定します。その層を修正します。もう一度実行します。これを 3 回から 5 回繰り返し、各ラウンドでの改善を記録してください。
