# テンプレートガイド (Template Guide)

このテンプレートは、プロジェクトにそのままコピーして使えるように用意されています。各ファイルは、エージェント(agent)のワークフローにおける特定の目的のために設計されています。プロジェクトのコマンド、パス、機能名、検証手順に合わせて内容を調整してください。

## 始め方

まず、プロジェクトのルートに次の4つのファイルをコピーしてください。

1. `AGENTS.md` または `CLAUDE.md`
2. `init.sh`
3. `claude-progress.md`
4. `feature_list.json`

プロジェクトの成長に合わせて、残りのファイルも追加してください。

---

## AGENTS.md

ルート用の指示ファイルです。エージェントがセッションを開始したときに最初に読むファイルで、コードを書く前に何をすべきか、どのように作業するか、どのように締めくくるかといった運用ルールを定義します。

**使い方:**

- プロジェクトのルートディレクトリにコピーしてください。
- 開始ワークフローの手順を、実際のプロジェクトのパスとコマンドに置き換えてください。
- チームのコンベンション(convention)に合わせて作業ルールを調整してください。
- "完了の定義(Definition of Done)" セクションは最も重要なので、必ず残してください。

**エージェントに与える役割:**

- 作業開始前に、進行状況と機能(feature)の状態を先に読むよう指示します。
- 一度に1つの機能だけを扱うよう強制します。
- 完了の印を付ける前に証拠(evidence)を求めます。
- セッション終了時に、リポジトリをクリーン状態(clean state)で終える方法を定義します。

Codex や他のエージェントには `AGENTS.md` を使ってください。Claude Code と一緒に作業する場合は `CLAUDE.md` を使ってください。構成は同じで、Claude の指示スタイルに合わせて整形されています。

## init.sh

開始スクリプトです。依存関係のインストール、検証(verification)、開始コマンドの出力をまとめて実行します。

**使い方:**

- プロジェクトのルートにコピーしてください。
- 先頭にある次の3つの変数を編集してください。
  - `INSTALL_CMD` — 依存関係のインストールコマンド（例: `npm install`, `pip install -r requirements.txt`）
  - `VERIFY_CMD` — 基本の検証コマンド（例: `npm test`, `pytest`）
  - `START_CMD` — 開発サーバーの起動コマンド（例: `npm run dev`）
- 実行権限を付与してください: `chmod +x init.sh`

**動作:**

1. 現在のディレクトリを出力します（正しい場所で実行されているか確認するため）。
2. 依存関係をインストールします。
3. 検証コマンドを実行します。
4. 開始コマンドを出力します（`RUN_START_COMMAND=1` が設定されている場合は直接実行します）。

検証に失敗した場合、エージェントは他の作業を始める前に、まず基準状態(baseline)を修正しなければなりません。

## claude-progress.md

進行ログ(progress log)です。すべてのセッションをこのファイルに記録し、新しいセッションはこのファイルを最初に読みます。

**使い方:**

- プロジェクトのルートにコピーしてください。
- "現在検証済みの状態(Current Verified State)" セクションを、プロジェクト情報で埋めてください。
- 各セッション後に、セッションレコードを更新してください。

**各フィールドの意味:**

- **現在検証済みの状態(Current Verified State)** — プロジェクトの現在状態を示す単一の真実の源
  - `Repository root directory` — プロジェクトの場所
  - `Standard startup path` — プロジェクトを起動するコマンド
  - `Standard verification path` — テストを実行するコマンド
  - `Highest priority unfinished feature` — 次のセッションで取り組む項目
  - `Current blocker` — 行き詰まっている項目
- **Session Record** — セッションごとに1件
  - `Goal` — 計画した作業
  - `Completed` — 実際に完了したこと
  - `Verification run` — 実行したテスト
  - `Evidence recorded` — 記録した証拠
  - `Commits` — コミットした内容
  - `Known risks` — 壊れる可能性のあるもの
  - `Next best action` — 次のセッションの出発点

## feature_list.json

機能トラッカー(feature tracker)です。エージェントが実装すべきすべての機能一覧と、その状態(status)、検証手順、証拠を機械可読な形式で管理します。

**使い方:**

- プロジェクトのルートにコピーしてください。
- サンプルの機能を実際の機能に置き換えてください。
- 各機能には次が必要です。
  - `id` — 短い一意の識別子
  - `priority` — 整数。小さいほど優先度が高い
  - `area` — アプリのどの部分か（例: "chat", "import", "search"）
  - `title` — 短い説明
  - `user_visible_behavior` — 機能が動作したときにユーザーが見るもの
  - `status` — `not_started`, `in_progress`, `blocked`, `passing` のいずれか
  - `verification` — 動作確認のための手順
  - `evidence` — 検証合格を記録する証拠（エージェントが記入）
  - `notes` — 補足情報

**status の規則:**

- `not_started` — まだ作業していない
- `in_progress` — 現在作業中の機能（一度に1つだけ）
- `blocked` — 文書化された問題により進めない
- `passing` — 検証に合格し、証拠が記録済み

エージェントは、一度に1つの機能だけを `in_progress` にできます。

## session-handoff.md

セッション間の簡潔な引き継ぎ(handoff)ノートです。セッションが終わり、次のセッションがすばやく引き継げるようにしたい場合に使ってください。

**使い方:**

- プロジェクトのルートにコピーしてください。
- 各セッション終了時に記入してください（エージェントが記入することもあります）。

**各セクションが扱う内容:**

- **現在検証済みのもの(Currently verified)** — 動作確認できたものと実行した検証
- **今回のセッションでの変更点(Changes this session)** — 変更したコードまたはインフラ
- **まだ壊れているもの、または未検証のもの(Still broken or unverified)** — 既知の問題とリスク領域
- **次に取るべき最善の行動(Next best action)** — 次のセッションでやること、触らないこと
- **コマンド(Commands)** — 起動、検証、デバッグ用コマンドの参照

このファイルは小規模なセッションでは任意です。セッションが長い場合や、プロジェクトに複数のアクティブな領域がある場合に重要になります。

## clean-state-checklist.md

各セッション終了前に実行するチェックリストです。次のセッションがクリーン状態(clean state)で始められるよう、リポジトリが良好な状態か確認します。

**使い方:**

- プロジェクトのルートにコピーしてください。
- セッションを閉じる前に確認してください。
- エージェントも、セッション終了ルーチンの一部としてこれらの項目を確認する必要があります。

**確認項目:**

- 標準の起動パスが引き続き動作するか
- 標準の検証パスが引き続き実行できるか
- 進行ログが更新されているか
- 機能一覧が実際の状態を反映しているか（偽の `passing` 項目がないか）
- 未完了の作業が記録されないまま残っていないか
- 次のセッションが手動修正なしで続行できるか

## evaluator-rubric.md

エージェントの出力(output)品質をレビューするための採点表(scorecard)です。セッション後、またはプロジェクトのマイルストーン(milestone)で、作業が基準を満たしているか評価する際に使ってください。

**使い方:**

- プロジェクトのルートにコピーしてください。
- セッション後（または一連のセッション後）に、6つの観点でエージェントの作業を採点してください。
- 各観点は 0-2 点で採点します。

**6つの観点:**

1. **正確性(Correctness)** — 実装は目標動作と一致しているか?
2. **検証(Verification)** — 必要な確認が証拠付きで実際に実行されたか?
3. **スコープ規律(Scope discipline)** — エージェントは選択した機能範囲の中に収まっていたか?
4. **信頼性(Reliability)** — 結果は再起動または再実行後も維持されるか?
5. **保守性(Maintainability)** — コードと文書は次のセッションで十分理解できるか?
6. **引き継ぎ準備性(Handoff readiness)** — 新しいセッションが、リポジトリの成果物だけで続行できるか?

**結論の選択肢:**

- Accept — 基準を満たす
- Revise — 受け入れ前に修正が必要
- Block — 先に解決すべき根本的な問題がある

**重要: 評価者(evaluator)には調整(calibration)が必要です。** デフォルト設定では、エージェントは自己評価が得意ではありません。問題を見つけても、自分で承認する方向へ論理を組み立てがちです。次のように繰り返し調整してください。

1. 完了したスプリント(sprint)で評価者(evaluator)を実行します。
2. スコアを自分の人間としての判断と比較します。
3. 差がある箇所では、ルーブリック(rubric)の合格/不合格基準をより具体化します。
4. もう一度実行して、整合しているか確認します。
5. 評価者が人間のレビューと一貫して一致するまで繰り返します。

3〜5回の調整(calibration)ラウンドを想定してください。各変更内容を記録し、何が整合性の改善に役立ったか追跡できるようにしてください。

## quality-document.md

プロジェクト内の各製品ドメイン(domain)とアーキテクチャ(architecture)レイヤ(layer)を格付けする品質スナップショット(snapshot)です。個別のセッション成果物ではなく、コードベース(codebase)全体の健全性を時系列で追跡します。

**使い方:**

- プロジェクトのルートにコピーしてください。
- セッション開始前: コードベースで最も弱い部分を把握するために読みます。
- セッション後: 変更内容に応じて格付けを更新します。
- 時間の経過とともに: スナップショットを比較し、どのハーネス(harness)変更が実際にコードベースの健全性を改善したか確認します。

**格付け対象:**

- **製品ドメイン(Product domains)**（例: ドキュメント取り込み、Q&A フロー、インデックス化）: 各ドメインは、検証状態、エージェント可読性(agent legibility)、テスト安定性、主要なギャップについて A-D の評価を受けます。
- **アーキテクチャレイヤ(Architectural layers)**（例: main process, preload, renderer, services）: 各レイヤは、境界の強制(boundary enforcement)とエージェント可読性について評価を受けます。

**重要性:**

評価者ルーブリックは個々のエージェント成果物を採点します。品質ドキュメントはコードベースそのものを採点します。2つの文書は別々の問いに答えます。

- 評価者ルーブリック(evaluator rubric): "エージェントは今回のセッションで良い仕事をしたか?"
- 品質ドキュメント(quality document): "プロジェクトは時間とともに強くなっているか、弱くなっているか?"

**更新のタイミング:**

- 重要なセッションのたびに
- ベンチマーク(benchmark)比較の前に
- 片付けや簡素化の作業の後に
- 新しいエージェントやモデルをプロジェクトにオンボーディング(onboarding)するときに

**ハーネス簡素化との連動:**

品質ドキュメントはハーネス(harness)の簡素化も支援します。すべてのハーネス構成要素には、モデルができないことに関する前提が含まれています。モデルが進化するにつれて、これらの前提は古くなります。構成要素がまだ必要かどうかを確認するには、次の手順を実行してください。

1. 品質ドキュメントのスナップショット(snapshot)を取得します。
2. ハーネス構成要素を1つ削除します。
3. ベンチマーク用のタスク集合を実行します。
4. もう一度スナップショットを取得します。
5. 比較します。格付けが下がらなければ、その構成要素はオーバーヘッド(overhead)だったということです。下がった場合は復元します。
