# ARCHITECTURE.md

このファイルはシステム全体の最上位マップです。簡潔に保ち、必要に応じてより詳細な文書を参照するようにしてください。

アーキテクチャ文書は、エージェント(agent)がコードを変更する前に読むべきシステムマップとして機能します。ドメイン境界、レイヤーモデル、依存関係ルールを一か所に明示することで、エージェントがアドホック(ad-hoc)なアーキテクチャを作ってしまうのを防ぎます。

## レイヤーモデル

エージェントが場当たり的なアーキテクチャを発明しないように、固定された方向性モデルを使用します。

`Types -> Config -> Repo -> Service -> Runtime -> UI`

横断的関心事(cross-cutting concern)は、レイヤーを直接またぐのではなく、明示的なプロバイダー(provider)またはアダプター(adapter)の境界を通して導入しなければなりません。

## 依存関係の厳格ルール

- 下位レイヤーは上位レイヤーに依存してはいけません。
- UI はランタイムまたはサービス契約を迂回してはいけません。
- データアクセスはリポジトリ(repository)または同等のアダプターを通して行わなければなりません。
- 共有ユーティリティは汎用性を保ち、ドメインロジックを溜め込んではいけません。
- 新しい依存関係は、対応する計画書または設計文書で正当化されていなければなりません。

## 変更チェックリスト

アーキテクチャ関連のコードを修正するときは:

1. ドメインマップまたは許可された境界が変わった場合は、このファイルを更新します。
2. 根拠が変わった場合は、`docs/design-docs/` の関連設計文書(design doc)を更新します。
3. ルールを機械的に強制する必要があるなら、実行可能な検査を追加または更新します。
