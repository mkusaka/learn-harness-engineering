# AGENTS.md

このリポジトリは、長時間稼働するコーディングエージェント(coding agent)の作業に最適化されています。このファイルは短く保ってください。このファイルは system-of-record 文書へのルーティング層として使い、巨大な指示集にはしないでください。

## 開始ワークフロー

コードを変更する前に:

1. `pwd` でリポジトリのルートを確認する。
2. 現在のシステム構成図と依存関係ルールを把握するために `ARCHITECTURE.md` を読む。
3. どのドメインまたはレイヤーが最も脆弱かを確認するために `docs/QUALITY_SCORE.md` を読む。
4. `docs/PLANS.md` を読み、現在作業中のアクティブな実行計画(active execution plan)を開く。
5. `docs/product-specs/` で関連する製品仕様(product spec)を読む。
6. このリポジトリの標準のブートストラップ(bootstrap)および検証(verification)手順を実行する。
7. 基準検証が失敗した場合は、範囲を追加する前にまず基準を復旧する。

## ルーティングマップ

- `ARCHITECTURE.md`: ドメイン構成図、レイヤーモデル、依存関係ルール
- `docs/design-docs/index.md`: 設計判断(design decision)と中核となる方針
- `docs/product-specs/index.md`: 現在の製品動作と受け入れ目標
- `docs/PLANS.md`: 計画のライフサイクルと実行計画ポリシー
- `docs/QUALITY_SCORE.md`: 製品ドメインとレイヤーの健全性
- `docs/RELIABILITY.md`: ランタイムシグナル、ベンチマーク、再起動時の期待値
- `docs/SECURITY.md`: secret、サンドボックス、データ、外部動作ルール
- `docs/FRONTEND.md`: UI 制約、デザインシステムルール、accessibility 検査

## 作業契約

- 一度に1つの限定された計画または機能スライスだけで作業する。
- コードチェックだけで作業完了だと見なさない。実行可能な証拠(evidence)が必要である。
- 動作を変更した場合は、同じセッション内で整合する製品・計画・信頼性の文書を更新する。
- 繰り返し発生するレビュー指摘がある場合は、チャットで言い直すのではなく、機械的なルール・検査・リンターへ昇格させる。
- 生成された資料は `docs/generated/` に、外部参考資料は `docs/references/` に保管する。
- このファイルを増やすより、小さく現在の文書を追加することを優先する。

## 完了条件

次のすべての条件が満たされたときのみ、変更を完了と見なす。

- 目標動作が実装されている
- 必要な検証が実際に実行されている
- 証拠が関連する計画または品質文書から参照されている
- 影響を受ける文書が最新状態に保たれている
- リポジトリが標準の起動経路からきれいに再起動できる

## セッション終了

セッションを終了する前に:

1. アクティブな実行計画を更新する。
2. ドメインまたはレイヤーが意味のある変更を受けた場合は、`docs/QUALITY_SCORE.md` を更新する。
3. 先送りされた項目がある場合は、`docs/exec-plans/tech-debt-tracker.md` に新しい技術的負債(tech debt)として記録する。
4. 完了した計画は、適切なタイミングで `docs/exec-plans/completed/` へ移動する。
5. 明確な次の行動がある、再起動可能な状態でリポジトリを残す。
