# SOP: 観測可能性フィードバックループ(Observability Feedback Loop)

デバッグが遅いとき、エージェント(agent)が証拠なしに成功を主張するとき、またはランタイムの挙動がコードそのものより把握しづらいときは、この標準作業手順(SOP)を使用してください。

観測可能性(observability)とは、ログ、メトリック、トレースのようなランタイム信号を通じて、システム内部の状態を外部から推論できる能力を指します。フィードバックループ(feedback loop)は、こうした信号をエージェントがコードの確認だけでなく実行結果からも推論できるよう、反復可能に構成したものです。

## 目標

エージェントにローカルなフィードバックループを提供し、ログ、メトリック、トレース、実行可能なワークロードを通じて、コード確認だけでなく実行結果からも推論できるようにします。

## 最小構成

- アプリケーションが構造化ログを出力する
- アプリケーションが可能であればメトリックとトレースを出力する
- ローカルの fan-out または収集レイヤー
- ログ、メトリック、トレースを問い合わせるためのインターフェース
- 変更ごとに再実行できる反復可能なワークロードまたはユーザージャーニー

## 実行手順

1. 最も重要なゴールデンランタイムジャーニー(golden runtime journey)を定義する。
2. 起動とコアパスに構造化ログを追加する。
3. 有用であれば、レイテンシ、失敗回数、キュー深さのメトリックを追加する。
4. 遅い、または複数段階に分かれたフローにトレースまたはタイミングマーカーを追加する。
5. ローカル開発環境で信号をクエリ可能にする。
6. エージェントに再実行するための反復可能なワークロードまたはシナリオを1つ与える。
7. ループを強制する: クエリ -> 相関分析 -> 推論 -> 実装 -> 再起動 -> 再実行 -> 検証。

## デバッグセッションのチェックリスト

- 何が失敗したのか?
- どの信号が失敗を証明しているのか?
- どのレイヤーがその失敗を所有しているのか?
- 修正後に何が変わったのか?
- アプリはきれいに再起動されたか?
- 再実行後に同じワークロードは通過したか?

## 完了条件

- エージェントがランタイムの証拠から失敗モードを説明できる。
- 各変更後に同じワークロードを再実行できる。
- 再起動と再実行が通常の作業ループの一部になっている。
- 信頼性(reliability)信号が `docs/RELIABILITY.md` に文書化されている。
