# SOP: 層状ドメインアーキテクチャ (Layered Domain Architecture)

エージェント(agent)が境界を繰り返し破ったり、階層間でロジックを重複実装したり、数回のセッション後にレビューしづらいコードを生成したりする場合は、この標準作業手順書(SOP)を使用してください。

層状アーキテクチャ(layered architecture)とは、コードベースを役割ごとの層に分け、各層間の依存方向を明示的に定めることで、エージェントが構造を静かに壊さずに素早く作業できるようにする設計原則です。

## 目標

ドメイン境界を明示して、エージェントが構造を静かに損なうことなく、素早く移動できるようにします。

## 目標モデル

ビジネスドメイン内では、次のような方向の流れを優先してください。

`Types -> Config -> Repo -> Service -> Runtime -> UI`

横断的関心事(cross-cutting concern)は、明示的なプロバイダー(provider)またはアダプター(adapter)を通して入る必要があります。共有ユーティリティはドメインの外側に置き、ドメインロジックを蓄積してはいけません。

## 設定チェックリスト

- `ARCHITECTURE.md` に現在のドメインを定義する。
- `ARCHITECTURE.md` に許可された依存方向を記録する。
- auth、テレメトリ(telemetry)、外部 API などの横断的関心事インターフェースを記録する。
- 現在もっとも問題になっている境界違反について、短いメモを1つ追加する。
- リント、テスト、またはスクリプトで機械的に強制する項目を決める。

## 実行手順

1. 実装スタイルに手を付ける前に、コードベースをドメインごとに対応付ける。
2. 各ドメインについて、許可された層の順序を確認する。
3. すべての横断的関心事を特定し、プロバイダーまたはアダプター経由でルーティングする。
4. 曖昧な共有ロジックは、所有するドメインへ移すか、真に汎用的なユーティリティとして分離する。
5. ルールを `ARCHITECTURE.md` に文書化する。
6. 最もコストの高い違反に対して、1つの実行可能なガードレール(guardrail)を追加する。
7. 変更後に品質スコアを更新する。

## 完了定義

- 新しいエージェントが、どの層が変更を所有するか理解できる。
- UI コードが、もはやリポジトリや外部の副作用に直接アクセスしない。
- 横断的関心事に、名前付きの入口がある。
- 少なくとも1つの重要な境界が機械的に強制される。

## 更新が必要なリポジトリ成果物

- `ARCHITECTURE.md`
- `docs/QUALITY_SCORE.md`
- `docs/design-docs/` — 根拠が変わった場合
- `docs/PLANS.md` またはアクティブな実行計画(execution plan)
