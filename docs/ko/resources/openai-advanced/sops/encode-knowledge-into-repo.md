# SOP: 目に見えない知識をリポジトリに組み込む

重要なコンテキスト(context)がまだ Google Docs、チャットスレッド、チケット、あるいは人々の頭の中にしかない場合は、この標準作業手順(SOP)を使ってください。

エージェント(agent)にとって見えない知識とは、リポジトリのどこにも記録されておらず、新しいセッションでは見つけられない暗黙知を指します。これをリポジトリ内のローカルファイルへ移すことが、system-of-record としてのリポジトリ原則の核心です。

## 目的

エージェントにとって見えない知識をコードベースで発見可能にし、新しいセッションが過去の会話に依存せず、そのまま作業できるようにします。

## トリガー信号

- エージェントがシステムの動作を繰り返し質問する。
- 「Slack で決めました」や「先週 X が言っていたとおりにしてください」といった言葉が出てくる。
- レビューで、リポジトリ内に記録されていないプロダクトまたはセキュリティ規則が参照される。
- 新しいセッションが、すでに解決済みであるはずの探索作業を繰り返す。

## 実行手順

1. 目に見えない知識の出所を一覧化する: 文書、チャット、暗黙のチーム規則、口頭での決定。
2. 各出所について問いかける: これはアーキテクチャ、プロダクトの挙動、セキュリティポリシー、信頼性(reliability)の期待値、計画コンテキスト、または参考資料のどれか?
3. 該当するリポジトリアーティファクト(artifact)へ組み込む:
   - アーキテクチャ -> `ARCHITECTURE.md`
   - プロダクトの挙動 -> `docs/product-specs/`
   - 設計根拠 -> `docs/design-docs/`
   - 実行状態 -> `docs/exec-plans/`
   - 繰り返し参照する外部資料 -> `docs/references/`
   - 品質または信頼性の期待値 -> `docs/QUALITY_SCORE.md` または `docs/RELIABILITY.md`
4. 曖昧な記述を、運用上役に立つ表現に置き換える。
5. 古いコピーを削除または deprecate して、リポジトリが単一の発見可能な真実を保てるようにする。

## 正しい組み込み規則

- 文学的な完成度ではなく、発見可能性のために書く。
- 分かりやすいファイル名を持つ短い文書を優先する。
- 関連する成果物どうしを相互にリンクする。
- 議事録ではなく、継続的に適用されるルールを保存する。
- 決定が下されたのと同じセッションでリポジトリを更新する。

## 完了定義

- 新しいエージェントが、人に尋ねなくても関連ルールを見つけられる。
- 同じ事実が、複数の矛盾したファイルに散らばっていない。
- 新しい成果物は、それが管轄するコードまたはワークフローの近くに配置されている。
