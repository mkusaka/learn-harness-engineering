# 講義 01. 強力なモデルでも実行の信頼性は保証しない

私は AI の世界にはかなり慣れているつもりでした。Claude Pro を契約し、GPT-4o の API キーも持ち、SWE-bench のリーダーボードの数値まで覚えていました。そんなある日、ついに実際のプロジェクトを AI エージェント(agent)に任せてみました。結果はどうだったか。機能を 1 つ追加するとテストが壊れ、1 つバグを直すと 2 つ増え、20 分も熱心に実行した末に堂々と「完了」と宣言したのに、コードを見ると依頼した内容とはまったく違っていました。

エージェント(agent)とは、自律的に作業を進める AI ソフトウェアの単位です。コーディングエージェント(coding agent)は、その中でもコード作成・リファクタ・テストなどの開発作業を担当します。

最初に浮かぶ考えはこうでしょう。「このモデルはまだ足りない。もっと良いものに変えよう。」ただし、財布を取り出す前に、問題が本当にモデルにあるのかを先に確認する必要があります。

数字を見てみましょう。ベンチマークの数値は急速に更新されます。2025 年 9 月時点で、Anthropic は Claude Sonnet 4.5 が SWE-bench Verified で 77.2% に達したと公表しています。つまり、ベンチマーク上ではかなり強く見えるモデルでも、それは明確な課題説明と既存のテストケースが揃った厳選タスクでの結果です。曖昧な要件、テストなし、暗黙のビジネスルールが散らばる実際の開発現場に持ち込めば、その数値はそのまま再現されません。

しかし、この数字の背後には、直感に反する真実があります。

## 同じ馬、違う結果

Anthropic は統制実験を行いました。同じプロンプト("2D レトロゲームメイカーを作れ")、同じモデル(Opus 4.5)。1 回目の実行は、何の支援もない丸腰の状態で、20 分、9 ドル、ゲームの中核機能はまったく動きませんでした。2 回目の実行は、完全なハーネス(harness)を適用し、プランナー + ジェネレーター + エバリュエーターの 3 エージェントアーキテクチャで、6 時間、200 ドル、実際に遊べるゲームができました。

ハーネス(harness)とは、AI コーディングエージェントが安定して動作するように、環境・状態(state)・検証(verification)・制御を束ねて提供する外骨格(スキャフォールディング)システムです。モデルの重みの外側にあるすべてのエンジニアリングインフラがハーネスに当たります。

モデルは変えていません。Opus 4.5 は最後まで Opus 4.5 のままでした。変わったのはサドルでした。

OpenAI が 2026 年に公開したハーネスエンジニアリングに関する記事は、はっきりこう述べています。整備されたリポジトリ(repository)での Codex は、「不安定」から「安定」へと質的転換を遂げる、と。注目すべきはその表現です。「少し良くなった」ではなく、質的な変化だということです。競走馬のようなものです。鞍なしでも乗れますが、遠くへは行けず、速くも走れず、落馬しても驚きではありません。ハーネスはその鞍です。**モデルの重みの外側にあるエンジニアリングインフラ全体**を指します。

## エージェントが実際に詰まる場所

では、具体的には何がうまくいかないのでしょうか。

最もよくある原因は、作業を明確に定義していないことです。「検索機能を追加して」と言っても、エージェントの理解はあなたの理解とはまったく違うかもしれません。何を検索するのか。全文検索か、構造化検索か。ページネーションは必要か。ハイライトはあるのか。明示していない以上、エージェントは推測します。推測が当たれば運、外れれば最初から明確にしていた場合より修正コストが高くつきます。レストランで料理人に「魚で」とだけ伝えるようなものです。煮付けになるのか、蒸し物になるのか、鍋になるのかは運次第です。

たとえ明確に指示していても、プロジェクトにはエージェントが知らない暗黙のアーキテクチャ慣習があります。チームでは SQLAlchemy 2.0 の記法を標準にしていても、エージェントはデフォルトで 1.x のコードを書きがちです。すべての API エンドポイントは OAuth 2.0 認証を使う必要があるのに、そのルールはあなたの頭の中と、3 か月前の Slack メッセージにしかありません。エージェントはそれを見られません。守りたくないからではなく、そのルールの存在自体を知らないからです。

環境も落とし穴です。不完全な開発環境、足りない依存関係、誤ったツールのバージョン。エージェントは本来の作業ではなく、`pip install` の失敗や Node のバージョン不一致への対応に貴重なコンテキストウィンドウ(context window)を消費します。熟練の大工を雇ったのに、金槌も釘も平らな作業台も渡していないようなものです。どれだけ腕が良くても、仕事はできません。

よりよくある問題は、検証(verification)の手段がそもそもないことです。テストもなく、リンタもなく、エージェントに渡す検証コマンドもありません。エージェントはコードを書き、見直し、問題ないと判断し、「完了」と宣言します。答え合わせなしで宿題を提出させるようなものです。学生は正解したつもりでも、採点すると誤りだらけです。Anthropic は興味深い現象も観察しました。エージェントがコンテキスト不足を検知すると、急いで終わらせようとし、検証を飛ばし、最善ではなく最も単純な解決策を選びます。これを「コンテキスト不安(context anxiety)」と呼びます。試験時間がほとんど残っていないときに、残った択一問題を適当に埋め始めるのと同じです。

セッションをまたぐ長時間作業では、状況はさらに悪化します。前のセッションで見つけたことはすべて失われ、毎回の新しいセッションでプロジェクト構造を再探索し、コード構成を再理解しなければなりません。永続的な状態(state)を持たないエージェントは、30 分を超える作業で失敗率が急激に上がります。

## 重要用語

こうしたシナリオを踏まえると、次の概念は単なる専門用語以上の意味を持ちます。

- **能力ギャップ(Capability Gap)**: ベンチマーク性能と実際の作業性能の大きな差。SWE-bench Verified で高い通過率が出ていても、実際の課題では要件の曖昧さ、暗黙の設計規約、検証不足によって結果が大きく落ちることがあります。
- **ハーネス(Harness)**: モデルの外側にあるすべてのもの。指示、ツール、環境、状態(state)管理、検証(verification)フィードバック。モデルの重みでなければ、すべてハーネスです。私たちが「鞍」と呼んでいるものです。
- **ハーネス起因の失敗(Harness-Induced Failure)**: モデルには十分な能力があるのに、実行環境に構造的な欠陥がある場合。Anthropic の統制実験がすでにこれを示しています。
- **検証ギャップ(Verification Gap)**: エージェントが自分の成果物(deliverable)に対して持つ自信と、実際の正確性の差。エージェントが「完了した」と言っても完了していない状態です。これが最も一般的な失敗です。
- **診断ループ(Diagnostic Loop)**: 実行 → 失敗を観察 → 特定のハーネスレイヤーに帰属 → そのレイヤーを修正 → 再実行。これがハーネスエンジニアリングの中心的な方法論です。
- **完了基準(Definition of Done)**: 機械的に検証可能な条件の集合。テスト合格、リンタがクリーン、型チェック合格。明示的な完了基準がなければ、エージェントは自分なりの基準を作ってしまいます。

## 失敗したらまずハーネスを点検する

中心となる原則はこうです。**失敗が起きたら、まずモデルを交換するのではなくハーネスを点検してください。** 同じモデルが、似たように整えられた作業で成功するなら、ハーネスの問題だと考えてください。車が故障したときに、いきなりエンジンを疑わないのと同じです。まず燃料があるかを確認します。

具体的な手順:

**すべての失敗を特定のレイヤーに帰属させてください。** 「モデルがいまいちだ」とだけ言わないでください。次のように問いましょう。作業の定義が曖昧だったのか。コンテキスト(context)が不十分だったのか。検証手段がなかったのか。各失敗を、5 つの失敗レイヤー(作業仕様、コンテキスト提供、実行環境、検証フィードバック、状態管理)のいずれかに割り当ててください。この習慣をつけると、ログから「モデルが足りない」という言葉がだんだん消えていきます。

**すべての作業に明示的な完了基準を書いてください。** 「検索機能を追加して」とは書かないでください。こう書きます。
```
完了基準:
- 新しいエンドポイント GET /api/search?q=xxx
- ページネーション対応、既定 20 件
- 結果にハイライトされたスニペットを含める
- 新規コードはすべて pytest を通過
- 型チェック通過 (mypy --strict)
```

**AGENTS.md ファイルを作成してください。** リポジトリ(repository)のルートに置き、エージェントにプロジェクトの技術スタック、アーキテクチャ慣習、検証コマンドを伝えてください。これはハーネスエンジニアリングの第一歩であり、費用対効果が最も高い一歩です。AGENTS.md ファイル 1 つの効果は、より高価なモデルにアップグレードするより大きいかもしれません。これは冗談ではありません。

**診断ループを構築してください。** 失敗を「またモデルが変なことをした」で終わらせないでください。ハーネスに欠陥があるサインとして扱ってください。失敗のたびにレイヤーを特定して修正し、同じ種類の失敗を繰り返さないようにしてください。数ラウンド回せば、ハーネスは強化され、エージェントの性能は安定します。道路補修のようなものです。穴を埋めるほど、次の区間はより滑らかになります。

**改善を定量化してください。** 簡単なログを残しましょう。各タスクが成功したか失敗したか、そしてどのレイヤーが失敗を引き起こしたかを記録します。数ラウンド後には、どのレイヤーがボトルネックかが見え始めます。そこに集中してエネルギーを使ってください。

## 百万行コード実験

OpenAI が 2026 年に公開した記事では、2025 年後半に空の git リポジトリから始め、Codex を使って完全な社内プロダクトを構築した事例が紹介されています。5 か月後、リポジトリには約 100 万行のコードが生成されていました。アプリケーションロジック、インフラ、ツール、ドキュメント、社内開発ツールのすべてをエージェントが生成しました。3 人のエンジニアが Codex を運用し、約 1,500 件の PR を作成してマージしました。1 人あたり 1 日平均 3.5 件の PR です。

重要な制約は、**人間はコードを直接書かない** ことでした。これは単なる実験設定ではありません。エンジニアの主な仕事がもはやコードを書くことではなく、環境設計、意図の表現、フィードバックループの構築になったとき、何が変わるのかを強制的に明らかにするための設計でした。

初期の進捗は予想より遅めでした。Codex の能力が足りなかったのではなく、環境がまだ十分に整っていなかったからです。エージェントには、高レベルの目標を前進させるために必要なツール、抽象化、内部構造が不足していました。エンジニアの仕事は次第にこう変わりました。大きな目標を小さな構成要素(設計、コード、レビュー、テスト)に分解し、エージェントに組み合わせさせ、その構成要素を使ってさらに複雑な作業を可能にすることです。何かが失敗したときの解決策は、ほとんどの場合「もっと頑張れ」ではありませんでした。「エージェントには何が足りず、どうすれば理解可能で実行可能な形にできるか」でした。

この実験は、この講義の中心命題を直接証明しています。**同じモデルでも、丸腰の環境と完全なハーネス環境では、根本的に異なる成果物を生み出します。** モデルは変わっていません。変わったのは環境です。

> 出典: [OpenAI: Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)

## 現実的な例

あるチームは、中規模の Python Web アプリ(FastAPI + PostgreSQL + Redis、約 15,000 行)に新しい API エンドポイントを追加するため、Claude Sonnet を使いました。

最初は 1 文だけを与えました。「`/api/v2/users` の下にユーザー設定エンドポイントを追加して。」結果はどうだったか。エージェントはコンテキスト(context)ウィンドウの 40% をリポジトリ構造の探索に使い、見た目はもっともらしいがプロジェクトのエラーハンドリングパターンに従っていないコードを生成し、古い SQLAlchemy の文法を使い、エンドポイントに実行時エラーがあるまま完了を宣言しました。次のセッションでは、すべての探索作業をゼロからやり直す必要がありました。

その後、AGENTS.md(プロジェクトアーキテクチャと技術スタックのバージョン説明)、明示的な検証コマンド(`pytest tests/api/v2/ && python -m mypy src/`)、アーキテクチャ決定記録を追加しました。同じモデルが独立に 3 回実行されたすべてで成功し、コンテキスト効率も約 60% 向上しました。

モデルは変えていません。ハーネスを変えました。

## 要点まとめ

- モデル能力と実行信頼性は別物です。競走馬にも良い鞍が必要です。
- 失敗したら、まずハーネスを点検し、その次にモデルを確認してください。モデルの交換は最も高くつく選択肢です。そして、多くの場合モデルの問題ではありません。
- すべての失敗はシグナルです。ハーネスに構造的な欠陥があります。見つけて修正してください。
- 5 つの防御レイヤー: 作業仕様、コンテキスト提供、実行環境、検証フィードバック、状態管理。医師が最もよくある原因から順に除外するように、体系的に点検してください。
- AGENTS.md ファイル 1 つが、より高価なモデルへのアップグレードより効果的なことがあります。本当です。

## 練習問題

1. **比較実験**: よく知っているコードベースと、それなりに大きな修正作業を 1 つ選んでください。まずハーネス支援なしでエージェントを実行し、失敗を記録します。次に、明示的な検証コマンドを含む AGENTS.md を追加し、同じエージェントで再実行してください。結果を比較し、各失敗を 5 つの防御レイヤーのいずれかに帰属させてください。

2. **検証ギャップ測定**: 5 件のコーディング作業を選んでください。各作業の後に、エージェントが完了を主張したかを記録し、その後、独立したテストで実際の正確性を検証します。エージェントが実際には完了していないのに完了したと主張した割合を計算してください。それがあなたの検証ギャップです。次に、どの検証コマンドがその割合を下げられるか考えてください。

3. **診断ループ演習**: プロジェクト内で、エージェントが繰り返し失敗する作業を見つけてください。1 回実行して失敗を記録します。5 つのレイヤーのいずれかに帰属させます。そのレイヤーを修正します。もう一度実行します。3〜5 ラウンド繰り返し、そのたびに改善点を記録してください。
