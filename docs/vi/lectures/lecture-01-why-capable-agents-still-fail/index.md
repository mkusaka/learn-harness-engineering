# 講義 01. 強力なモデルでも、信頼できる実行にはならない

あなたは AI の世界では経験豊富だと自負しています。Claude Pro に登録し、GPT-4o の API key を持ち、SWE-bench のランキングの数字も頭に入っています。そんなあなたがある日、ついに本物のプロジェクトを AI agent に任せることにし、十分な自信を持って送り出しました。結果はどうだったでしょう。機能は追加されたのにテストは壊れ、1 つのバグを直したら別の 2 つのバグが増え、20 分動いて「完了」と堂々と宣言したのに、コードを見れば求めていたものとはまったく違っていた、という具合です。

最初の反応は何でしょうか。「このモデルは十分ではない。アップグレードすべきだ。」そう考えるかもしれません。ですが、その前に財布を開くのは早すぎます。問題は、モデルそのものではない可能性が十分にあります。

いくつか数字を見てみましょう。ベンチマークの数字は驚くほど速く変わります。2025 年 9 月には、Anthropic が Claude Sonnet 4.5 の SWE-bench Verified でのスコアが 77.2% だと発表しました。つまり、モデルがベンチマーク上では非常に強く見えても、それはあくまで、問題設定が明確で既存のテストがあるような、慎重に選ばれたタスクの結果にすぎません。日々の開発環境に持ち込んでみてください。曖昧な要求、テストなし、あちこちに散らばった暗黙のビジネスルール。そうなると、その数字が自動的に再現されるわけではありません。

しかし、この数字の裏には、直感に反する真実があります。

## 同じ馬でも、運命は違う

Anthropic は制御された実験を行いました。まったく同じ prompt（「2D レトロゲームジェネレーターを作る」）、まったく同じモデル（Opus 4.5）です。1 回目の実行は、何の支援もない裸の状態でした。20 分、$9、ゲームの中核機能はまったく動きません。2 回目の実行は、完全な harness（planner + generator + evaluator の 3 agent 構成）です。6 時間、$200、ゲームは遊べる状態になりました。

モデルは変わっていません。Opus 4.5 は相変わらず Opus 4.5 です。変わったのは鞍です。

OpenAI の 2026 年版 harness engineering の記事は、率直にこう述べています。優れた harness を備えたリポジトリでは、Codex は「信頼できない」状態から「信頼できる」状態に移るのだ、と。ここでの表現に注目してください。単に「少し良くなる」ではなく、質的な変化です。サラブレッドのようなものです。鞍なしでも乗れますが、遠くへも速くも進めず、落馬しても不思議ではありません。harness はその鞍です。**モデルの重み以外にある、技術基盤のすべて**です。

## Agent はどこで本当に詰まるのか

では、具体的には何がうまくいかないのでしょうか。

最もよくあるのは、タスクを明確に定義していないことです。あなたは「検索機能を追加して」と言いますが、agent の理解はあなたの理解とまったく違うかもしれません。何を検索するのか。全文検索なのか、構造化検索なのか。ページネーションは必要か。ハイライトは必要か。あなたが指定しないので、agent は推測します。推測が当たれば幸運、外れれば、最初から具体化したほうがずっと安かったはずです。レストランに入って「魚が欲しい」とだけ注文するようなものです。煮魚なのか、蒸し魚なのか、鍋なのかは完全に運任せです。

たとえ仕様を出していても、プロジェクトには agent の知らない暗黙のアーキテクチャ規約があります。あなたのチームは SQLAlchemy 2.0 の書き方に統一しているのに、agent は 1.x のコードを書きがちです。すべての API endpoint は OAuth 2.0 認証を使うべきなのに、そのルールはあなたの頭の中と、3 か月前の Slack メッセージにしかありません。agent はそれを見られません。守りたくないからではなく、本当にそのルールの存在を知らないからです。

環境も落とし穴です。dev environment が不完全で、dependencies が足りない、tool のバージョンが違う。agent は本来のタスクではなく、`pip install` のエラーや Node のバージョン衝突に大事な context window を食われます。まるで、腕のいい大工を雇ったのに、ハンマーも釘も平らな作業台も渡し忘れたようなものです。どれほど腕が良くても、仕事は進みません。

さらにありがちなのは、そもそも検証できる手段がないことです。テストがない、lint がない、あるいは検証コマンドが agent に伝わっていない。agent はコードを書いて、それを見て、問題ないと判断し、「完了」と言います。答えのない宿題を出された生徒のようなものです。本人は合っているつもりでも、採点すれば間違いだらけです。Anthropic は興味深い現象も観察しました。agent は context が尽きそうになると、急いで終わらせようとし、検証を飛ばし、最適解よりも簡単な解を選びがちです。これを彼らは「context anxiety」と呼びました。テストの時間が残り少ないことに気づいて、残った選択問題を勘で埋め始めるのと同じです。

複数の session にまたがる長いタスクはさらに悪化します。前の session で得た発見はすべて失われ、新しい session は毎回、プロジェクト構造を再発見し、コードの組み立て方を再学習しなければなりません。状態を持たない agent は、30 分を超えるタスクで失敗率が急上昇します。

## 重要な用語の説明

こうした状況では、次の概念はもはや単なる用語ではありません。

- **Capability Gap（能力ギャップ）**: ベンチマーク上のモデル性能と、実際のタスクでの性能の大きな差。SWE-bench Verified で高いスコアを出しても、曖昧な要求、暗黙のアーキテクチャ規約、検証不足がある現実の issue では、同じ結果を保証できません。
- **Harness**: モデルの外側にあるすべてのもの。指示、tool、environment、state management、検証フィードバック。モデルの重みでなければ、それは harness です。つまり、私たちが「鞍」と呼んでいるものです。
- **Harness-Induced Failure（harness に起因する失敗）**: モデルには十分な能力があるのに、実行環境に構造的な欠陥があるために失敗すること。Anthropic の制御実験がこれを示しました。
- **Verification Gap（検証ギャップ）**: agent が結果に抱く自信と、実際の正しさの差。まだ終わっていないのに「終わりました」と言ってしまうのが、最も一般的な失敗モードです。
- **Diagnostic Loop（診断ループ）**: 実行し、エラーを観察し、特定の harness 層に原因を割り当て、その層を修正し、再実行すること。これが harness engineering の中核となる方法論です。
- **Definition of Done（完了定義）**: 機械で検証できる条件の集まり。たとえば、テストが通る、lint がきれい、type check が通る、などです。明確な完了定義がなければ、agent は自分なりの定義を勝手に作ってしまいます。

## 問題が起きたら、まず harness を直す

核となる原則は、**問題が起きたら、まずモデルを変えるのではなく harness を確認すること**です。もし同じモデルが、似た構造のうまくいくタスクでは成功しているなら、まず harness の問題を疑ってください。車が動かなくなったときに、いきなりエンジンを疑わないのと同じです。まずはガソリンを確認します。

具体的な手順:

**各失敗を、特定の層に帰属させる。** ただ「モデルがよくない」と言わないでください。タスクは曖昧だったのか。context は不足していたのか。検証方法がなかったのか。各失敗を、5 つの防御レイヤーのどれか（タスク仕様、context 提供、実行環境、検証フィードバック、state management）にマッピングします。この習慣をつけると、ログの中で「モデルが十分ではない」という言葉はどんどん減っていきます。

**各タスクに明確な Definition of Done を書く。** 「検索機能を追加して」ではなく、こう書きます。
```
完了条件:
- 新しい GET /api/search?q=xxx エンドポイント
- ページネーション対応、デフォルト 20 件
- 結果にハイライト付きスニペットを含める
- 新しいコードはすべて pytest を通過
- type checking が通る (mypy --strict)
```

**AGENTS.md を作る。** リポジトリのルートに置き、agent にプロジェクトの tech stack、アーキテクチャ規約、検証コマンドを伝えます。これは harness engineering の最初の一歩であり、最も ROI が高い作業です。`AGENTS.md` は、より高価なモデルへアップグレードするより効果があることがあります。本気です。

**診断ループを構築する。** エラーを「またモデルが鈍かった」とは考えないでください。harness に構造的な欠陥があるというシグナルとして扱います。各エラーで層を特定し、その層を修正し、同じ失敗を二度と起こさないようにします。数回回せば、harness は強くなり、agent の性能も安定します。道路の穴埋めと同じです。1 つ埋めるたびに、その先の走行が少しずつ滑らかになります。

**改善を定量化する。** シンプルなログを残しましょう。各タスクが成功か失敗か、そしてどの層が失敗の原因だったかを記録します。数回繰り返すと、どの層がボトルネックかが見えてきます。そこに集中的に手を入れればよいのです。

## 百万行コードの実験

2026 年の記事で OpenAI は、2025 年後半に始まった大胆な実験を紹介しています。空の git リポジトリから、Codex を使って社内向けの完全なプロダクトを構築したのです。5 か月後、そのリポジトリには約 100 万行のコードがありました。アプリケーションロジック、インフラ、tooling、ドキュメント、社内 dev tool まですべて agent が生成したものです。3 人のエンジニアが Codex を運用し、およそ 1,500 件の PR を開き、マージしました。1 人あたり 1 日平均 3.5 PR です。

主な制約は、**人間は一切コードを書かないこと**でした。これは gimmick ではありません。エンジニアの主な仕事がコードを書くことではなく、環境を設計し、意図を明確に伝え、フィードバックループを構築することになったとき、何が変わるのかを強制的に明らかにするための設計です。

最初の進捗は予想より遅れていました。Codex に能力が足りなかったからではなく、環境が十分に整っていなかったからです。agent には、より高次の目標へ進むために必要な tool、抽象化、内部構造が不足していました。エンジニアの仕事は、大きな目標を小さな構成要素（設計、コーディング、評価、テスト）に分解し、agent にそれらを組み立てさせ、さらにその構成要素を使って、より複雑なタスクを解放していくことになりました。問題が起きたとき、答えはほとんどの場合「もっと頑張れ」ではありませんでした。むしろ「agent に何が欠けているのか、そしてどうすればそれを理解し、実行できるようにできるのか？」でした。

この実験は、この講義の核心を直接示しています。**同じモデルでも、裸の環境と完全な harness を備えた環境では、結果が本質的に異なる**のです。モデルは変わっていません。変わったのは環境です。

> 出典: [OpenAI: Harness engineering: leveraging Codex in an agent-first world](https://openai.com/index/harness-engineering/)

## もっと現実的な例

あるチームは Claude Sonnet を使って、中規模の Python Web アプリケーション（FastAPI + PostgreSQL + Redis、約 15,000 行）に新しい API endpoint を追加しました。

最初は「`/api/v2/users` の下にユーザー設定 endpoint を追加して」という一文だけを与えました。結果はどうだったか。agent は context window の 40% を使って repo の構造を探索し、見た目はもっともらしいが、プロジェクトのエラー処理パターンに従っておらず、古い SQLAlchemy の構文を使い、runtime error を含む endpoint を「完了」と宣言しました。次の session では、探索作業をほぼすべてやり直す必要がありました。

その後、彼らは `AGENTS.md`（プロジェクトのアーキテクチャと tech stack のバージョンを説明するもの）、明確な検証コマンド（`pytest tests/api/v2/ && python -m mypy src/`）、そしてアーキテクチャ判断の記録を追加しました。同じモデルは、3 回の独立した実行すべてで成功し、context 効率もおよそ 60% 向上しました。

モデルは変えていません。harness を変えたのです。

## 覚えておくべき要点

- モデルの能力と実行の信頼性は別物です。サラブレッドにも、ちゃんとした鞍が必要です。
- 問題が起きたら、まず harness を確認し、そのあとでモデルを疑ってください。モデルの変更は最も高くつく選択肢であり、そもそも問題がモデルではないことも多いです。
- すべての失敗は、harness に構造的な欠陥があるというシグナルです。それを見つけて、直してください。
- 5 つの防御レイヤー: タスク仕様、context 提供、実行環境、検証フィードバック、state management。最もありがちな原因から順に、医師のように体系的に切り分けていきます。
- `AGENTS.md` は、高価なモデルへのアップグレードより効果があることがあります。本当にそうです。

## 演習

1. **比較実験**: よく知っている codebase から、単純ではない変更タスクを 1 つ選んでください。まず harness の支援なしで agent を実行し、失敗を記録します。次に、明確な検証コマンドを含む `AGENTS.md` を追加し、同じ agent でもう一度実行します。結果を比較し、各失敗を 5 つの防御レイヤーのいずれかに帰属させてください。

2. **検証ギャップの測定**: 5 つのプログラミングタスクを選びます。各タスクのあとで、agent が「完了した」と宣言したかどうかを記録し、その後、独立したテストで実際の正しさを確認します。agent が完了を宣言したのに実際には未完だった割合を計算してください。それがあなたの verification gap です。次に、どの検証コマンドがこの割合を下げるか考えてみてください。

3. **診断ループの練習**: あなたのプロジェクトで、agent が繰り返し失敗するタスクを見つけます。1 回実行してエラーを記録し、5 つのレイヤーのうち 1 つに帰属させます。そのレイヤーを修正し、もう一度実行します。これを 3〜5 回繰り返し、毎回の改善を記録してください。
